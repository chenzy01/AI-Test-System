# 测试点提取技能（test-point-extraction）

## 一、技能定位

将需求（或需求分析产物）通过经典测试设计方法**系统化展开**为「全覆盖测试点集」。每个测试点声明推导方法、精确断言与所需数据，且与方法推导过程相互印证、可复核。

与相邻技能的分工：

- 上游 `requirements-analysis`：产出 REQ 基线、澄清清单（CL）、粗粒度初始 TP。
- 本技能：以设计方法对每个 REQ 做穷尽式展开、合并去重，产出细粒度全覆盖 TP 集。
- 下游 `testcase-generation`：将 TP 转化为可执行用例（**本技能不生成用例步骤**）。

## 二、编号契约（继承自 requirements-analysis，必须遵守）

| 前缀 | 含义 | 本技能行为 |
|------|------|-----------|
| REQ-xxx | 需求点 | 沿用上游编号；独立模式时快速建立基线（REQ-001 起，名称标注 `[快速基线]`） |
| CL-xxx | 澄清问题 | 沿用上游编号；依赖 CL 的 TP 必须在备注标注「依赖 CL-xxx 确认」 |
| TP-xxx | 测试点 | 本技能产出。消费上游报告时自其最大 TP 编号后接续，禁止重号；独立模式自 TP-001 起 |

- 每个 TP 回链 ≥1 个 REQ 且标注推导方法。
- 同一验证目标若由多个方法共同推导，保留一个 TP，「设计方法」列合并（如「等价类划分+边界值分析」）。

## 三、工作流程

按以下 6 个阶段顺序执行。

### 阶段 1：输入识别与预处理

判断输入类型，选择处理路径：

- **路径 A（标准）**：输入为需求分析报告，含 REQ/CL/TP 基线 → 直接进入阶段 2。
- **路径 B（独立）**：输入为原始需求文档 → 按 requirements-analysis 技能阶段 1–4 快速建立 REQ 基线（含隐性标注与 CL 登记），REQ 名称后标注 `[快速基线]`，并在报告风险提示中声明「建议补充完整需求分析确认隐性需求」。
- **路径 C（补全）**：输入为已有 TP 清单 → 先按 `references/coverage-rules.md` 第 2 节去重合并，再按阶段 4 查漏补缺；输出「新增 TP + 修订说明」，不重写已有 TP 编号。

### 阶段 2：方法选型

对每个 REQ，依据 `references/design-methods.md` 的方法选型表匹配设计方法：

- 含输入/输出可分类字段 → 等价类划分
- 含范围型字段（数值/长度/时间/数量） → 边界值分析
- 含多条件组合决定行为 → 判定表（组合数超限时按 `references/coverage-rules.md` 第 3 节裁剪）
- 含状态/生命周期 → 状态迁移
- 含端到端业务流 → 场景法
- 历史缺陷密集/高风险点 → 错误推测
- 多因素两两交互风险 → 成对组合

每个 REQ 至少匹配 1 个方法；REQ 不满足某方法适用条件时，在映射表中注明「不适用」，禁止硬套。选型结果输出为「REQ×方法」映射表。

### 阶段 3：逐方法展开（核心阶段）

按 `references/design-methods.md` 各方法的标准步骤逐 REQ 展开，产出候选测试点（CTP）：

- **等价类划分**：有效等价类与无效等价类全部覆盖；无效类必须覆盖 不传/类型错/超界/格式错 四种子类。
- **边界值分析**：对每个边界应用 7 类取值（最小/最大/临界±步长/空值/非法类型/超界/精度），临界值必须取「边界 ± 最小步长」。
- **判定表**：列出全部条件桩与动作桩，展开全部条件组合（或按裁剪规则裁剪并注明依据），每个规则列对应 ≥1 个 CTP，业务互斥组合标注「不可达」。
- **状态迁移**：以状态迁移表列出全部边（合法+非法），每条边对应 ≥1 个 CTP；非法边必须定义期望表现（拒绝 + 状态不变 + 具体错误码）。
- **场景法**：基本流 1 条 + 备选流 N 条 + 异常流 M 条，逐条对应 CTP，写明整条路径步骤序列与终点状态。
- **错误推测**：逐条写出推测依据（历史缺陷模式），无依据的推测不采纳。
- **成对组合**：列出因素与水平，生成两两覆盖组合表，每个组合对应 ≥1 个 CTP。

展开过程中，凡遇到上游 CL 未确认的规则 → 按 CL 建议默认值设计，TP 备注标注「依赖 CL-xxx 确认」。

### 阶段 4：合并去重与独立性校验

- 按 `references/coverage-rules.md` 第 2 节判定等价 CTP（同输入等价类 + 同断言目标 + 同后置状态），合并后重新连续编号，在推导附录标注合并来源。
- 拆分复合验证点：一个 CTP 含多个独立验证目标（如同时断言提示文案与数据回滚）→ 拆分为多个 TP。
- 形成最终 TP 集。

### 阶段 5：覆盖度自检

按 `references/coverage-rules.md` 第 1 节指标逐项核对并输出覆盖矩阵：

- 需求点覆盖率 = 100%（无孤儿 REQ）；
- 每个 REQ ≥ 功能/边界/异常 三类（无对应维度时备注理由）；
- 每个范围字段 ≥ 1 组 临界±步长 TP；
- 判定表条件组合全覆盖或注明裁剪；状态迁移边全覆盖（含非法边）。

不达标 → 回阶段 3 补点，禁止带着覆盖空洞输出。

### 阶段 6：输出

按第 4 节输出契约生成报告，对照 `templates/testpoint-output-template.md` 检查字段完整性。

## 四、输出契约

### 4.1 测试点全表（核心产物）

| 测试点ID | 关联需求点 | 测试点名称 | 测试类型 | 设计方法 | 输入与前置状态 | 期望输出与后置状态（精确断言） | 所需测试数据 |
|---------|-----------|-----------|---------|---------|----------------|-------------------------------|-------------|

列定义同 requirements-analysis 4.2；「设计方法」可多值，用「+」连接。

### 4.2 覆盖矩阵

REQ × 测试类型 二维表，单元格填写该组合的 TP 编号列表（无则填「—」并备注理由）。

### 4.3 方法推导附录

逐 REQ 附推导过程（等价类表/边界值表/判定表/状态迁移表等），格式见 `references/design-methods.md` 各方法「产出物」小节；表格行必须与最终 TP 一一对应（每行标注产出 TP 编号）。

### 4.4 报告结构

```
# 测试点提取报告
## 1. 输入说明与处理路径（A/B/C）
## 2. REQ×方法 映射表
## 3. 测试点全表（TP）
## 4. 覆盖矩阵（REQ×测试类型）
## 5. 方法推导附录
## 6. 裁剪说明与风险提示
```

## 五、质量门禁（输出前逐项自检，不通过则修订后重新输出）

1. **可断言性**：沿用 requirements-analysis 禁词清单（`references/extraction-rules.md` 第 5 节）；期望输出必须含具体字段+具体值/状态。
2. **方法真实性**：声明的方法必须体现在推导附录中（如声明边界值分析，附录必有边界表且含 ±步长 取值）；附录表格行与 TP 一一对应，禁止「有方法无推导、有推导无 TP」。
3. **全覆盖性**：阶段 5 指标全部达标。
4. **独立性**：TP 两两无重复；每个 TP 只验证一个验证点。
5. **可追溯性**：编号连续；TP 回链的 REQ 存在；依赖 CL 的 TP 已标注。
6. **可执行性**：所需测试数据含具体值且可直接构造。

## 六、约束与禁止事项

- 只产出测试点，不生成用例步骤、不生成代码。
- 禁止为凑方法而硬套：REQ 不满足方法适用条件时注明「不适用」，不强制造点。
- 组合裁剪必须注明裁剪依据与遗漏风险，禁止静默裁剪。
- 用户指定方法时优先按用户方法展开；用户未指定时按阶段 2 选型。
