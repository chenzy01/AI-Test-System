# 需求分析技能（requirements-analysis）

## 一、技能定位

将"自然语言需求"转化为"可测试规格"。本技能产出两件产物：

1. **需求澄清清单（CL）**：需求中无法直接测试或存在歧义的点，形成可向产品/开发提出的精确问题。
2. **可测试点矩阵（TP）**：可独立验证、可精确断言的测试点全集，供下游 `test-point-extraction` 与 `testcase-generation` 技能直接消费。

## 二、编号契约（全链路全局约定，下游技能必须复用）

| 前缀 | 含义 | 格式 | 说明 |
|------|------|------|------|
| REQ | 需求点 | REQ-001 | 从需求中识别出的最小可测功能单元，全链路追溯锚点 |
| CL  | 澄清问题 | CL-001 | 需求歧义/缺口问题，必须为封闭式问题（可给出具体值/选项） |
| TP  | 测试点 | TP-001 | 单一验证目标，一个测试点只验证一件事 |

- 编号在单次任务内从 001 递增，禁止跳号、禁止复用已删除编号。
- 每个 TP 必须回链 ≥1 个 REQ；每个 CL 必须回链 ≥1 个 REQ。
- 下游技能（test-point-extraction 输出 TP、testcase-generation 输出 TC）必须复用本技能产出的 REQ/TP 编号，保证全链路可追溯。

## 三、工作流程

按以下 6 个阶段顺序执行。任一阶段发现信息不足时，先登记到澄清清单（CL）再继续，禁止停下等待或臆造。

### 阶段 1：输入识别与完整性校验

- 确认输入来源与类型（文档全文 / 用户口述 / 接口文档 / 原型图描述），并说明识别依据。
- 逐项执行完整性校验：

  - [ ] 角色/权限描述存在（谁可以用、谁不能）
  - [ ] 业务规则存在（校验、计算、状态流转）
  - [ ] 数据字段定义存在（名称、类型、长度、取值范围、精度、必填性）
  - [ ] 异常场景描述存在（失败、超时、重复、并发）
  - [ ] 验收标准存在（可观察的结果）

- 缺失项 → 立即登记为 CL（问题类型=信息缺失），并继续在后续阶段挖掘相关缺口。

### 阶段 2：显性需求提取（→ REQ）

- 以「单一功能单元」为粒度拆分需求点，编号自 REQ-001 起。
- 每个 REQ 必须包含：编号、名称、需求原文（逐字引用）、来源位置、触发条件、处理逻辑、输出结果。
- 拆分判据（满足其一即独立成 REQ）：
  1. 能被独立开发与独立验收；
  2. 有独立触发入口（按钮/接口/定时任务/事件）；
  3. 与其他功能点存在不同的业务规则。
- 禁止将多个不相关功能合并为一个 REQ；禁止将同一功能拆成碎片化 REQ。

### 阶段 3：隐性需求挖掘（→ 隐性 REQ）

- 依据 `references/extraction-rules.md` 第 1 节的 9 大挖掘维度（数据约束、状态流转、权限隔离、并发一致性、异常恢复、性能容量、兼容适配、安全合规、可审计性），对每个 REQ 逐一过筛。
- 规则：凡需求未明说、但"不满足则功能不可上线"的规则 → 补登记为隐性 REQ，名称后标注 `[隐性]`，来源标注"推断"。
- 凡无法确定规则内容（如阈值、时效、上限）→ 登记 CL，问题必须具体到字段与数值。
- 禁止臆造需求未提及且无业务依据的规则；无法判定时登记 CL 而非自行假定。

### 阶段 4：边界规则与异常流程识别

- 对每个含 数值/长度/时间/数量/集合/枚举 的字段，按 `references/extraction-rules.md` 第 2 节的边界识别规则（最小值/最大值/临界±最小步长/空值/非法类型/超界值/精度边界）提取边界点。
- 对每个 REQ，按 `references/extraction-rules.md` 第 3 节的 8 类异常清单（输入非法、依赖失败、重复提交、并发冲突、权限不足、资源耗尽、超时中断、数据异常）逐项筛查。
- 识别结果并入可测试点矩阵，测试类型标记为「边界」或「异常」。

### 阶段 5：生成需求澄清清单（→ CL）

对阶段 1–4 登记的所有问题执行质量校验，确保每个 CL：

- 精确到具体字段/对象/操作，如「扣款前置校验的字段是『可用余额』还是『账户总额（含冻结）』？」；
- 是封闭式问题（可给出具体值/选项），禁止开放式提问（如"这个功能怎么做？"）；
- 给出「建议默认值」与「影响范围」（若按建议实现，影响哪些 REQ/TP）；
- 按严重程度分级：**P0**=不澄清则无法设计用例；**P1**=不澄清则存在高风险误测；**P2**=优化性确认；
- 按第 4.1 节表格输出，禁止在 CL 中混入解决方案讨论。

### 阶段 6：生成可测试点矩阵（→ TP）

- 每个 REQ 至少产出 3 类测试点：正常流程、边界、异常；若某 REQ 确实无边界/异常维度，必须在备注中说明理由。
- 每个 TP 必须：
  1. 回链 REQ 编号；
  2. 声明设计方法（等价类划分/边界值分析/判定表/状态迁移/场景法/错误推测，选择规则见 `references/extraction-rules.md` 第 4 节）；
  3. 写明可观察断言：`输入 + 前置状态 → 期望输出 + 后置状态`，断言必须精确到字段与数据状态（见质量门禁第 1 条）；
  4. 写明所需测试数据（含具体数值与数据状态，可直接构造）。
- 按第 4.2 节表格输出；测试点之间禁止重复，一个 TP 只验证一个明确验证点。

## 四、输出契约

### 4.1 需求澄清清单（Markdown 表格）

| 问题ID | 问题类型 | 关联需求点 | 严重程度 | 问题描述（精确到字段/数值） | 建议默认值 | 影响范围 |
|--------|---------|-----------|---------|------------------------------|-----------|---------|

问题类型枚举：信息缺失 / 规则歧义 / 边界未定义 / 状态流转缺失 / 异常场景缺失 / 数据定义缺失 / 验收标准缺失 / 角色权限缺失。

### 4.2 可测试点矩阵（Markdown 表格）

| 测试点ID | 关联需求点 | 测试点名称 | 测试类型 | 设计方法 | 输入与前置状态 | 期望输出与后置状态（精确断言） | 所需测试数据 |
|---------|-----------|-----------|---------|---------|----------------|-------------------------------|-------------|

测试类型枚举：功能 / 边界 / 异常 / 状态流转 / 权限 / 并发 / 性能 / 兼容性 / 安全。

### 4.3 报告结构总览

```
# 需求分析报告
## 1. 需求概览（需求点总数、显性/隐性分布、CL/TP 数量统计）
## 2. 需求点清单（REQ 全表，含原文引用与来源）
## 3. 需求澄清清单（CL 表）
## 4. 可测试点矩阵（TP 表）
## 5. 风险提示（无法覆盖区域、依赖外部系统的测试点、数据构造难点）
```

完整带注释示例见 `templates/analysis-output-template.md`；输出前必须对照该模板检查字段完整性。

## 五、质量门禁（输出前逐项自检，不通过则修订后重新输出）

1. **可断言性**：每个 TP 的「期望输出」必须写明具体字段名与具体值/状态（如「订单状态字段 status 由 pending 变更为 paid」「返回错误码 40021 且余额字段保持 100.00 不变」）。命中 `references/extraction-rules.md` 第 5 节禁词清单（"校验通过""提示合理""显示相关提示""处理正确"等）即视为不合格。
2. **可执行性**：每个 TP 的「输入与前置状态」「所需测试数据」足以让测试人员不查任何文档即可构造数据并执行。
3. **全覆盖性**：REQ → TP 无孤儿需求点；每个 REQ 至少覆盖 正常/边界/异常 三类。
4. **澄清问题质量**：每个 CL 都是封闭式问题且含建议默认值；CL 中不存在开放式表述。
5. **可追溯性**：REQ/CL/TP 编号连续，交叉引用无悬空（TP/CL 引用的 REQ 必须存在）。
6. **零臆造**：所有推断性内容已标注 `[隐性]`/「推断」；未标注条目必须能在原文中找到出处。

## 六、约束与禁止事项

- 只依据输入材料分析，禁止编造材料中不存在的功能；确有业务常识性补充时，必须标注 `[隐性]` 并同步写入 CL 待确认。
- 本技能只产出 CL + TP，不生成用例、不生成代码；用例编写交给下游技能。
- 输入为多份文档时，先做需求合并与冲突检测（同一功能多处描述不一致 → 登记 CL，类型=规则歧义）。
- 用户要求裁剪输出（如只输出澄清清单）时，按用户裁剪执行，但质量门禁中与该产物相关的条目仍必须通过。
