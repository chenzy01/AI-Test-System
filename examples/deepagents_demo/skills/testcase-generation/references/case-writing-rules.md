# 用例编写规范库（references/case-writing-rules）

> 渐进式披露文件：SKILL.md 阶段 3/4 引用本文件。所有规范配 好例/坏例 对照。

## 1. 测试步骤编写规范

| 规则 | 要求 | 好例 | 坏例 |
|------|------|------|------|
| R1 单动作 | 一步 = 一个动作 + 一个对象 + 具体数据值 | 「在数量输入框输入 11」 | 「输入数据」 |
| R2 数据具体 | 所有输入值写具体值，禁止泛指 | 「在搜索框输入『华为手机』」 | 「输入关键字」 |
| R3 动作可观察 | 动作用词明确（点击/输入/选择/调用/查询/等待） | 「点击『提交订单』按钮」 | 「提交订单」 |
| R4 步骤不含预期 | 系统自动行为写入预期列，不写入步骤 | 步骤「点击『余额支付』按钮」+ 预期「支付成功，余额字段由 100.00 变更为 50.00」 | 步骤「点击支付按钮，系统扣减余额」 |
| R5 接口步骤全要素 | 方法 + URL + 请求体字段与值 | 「调用 POST /payment/pay，body: {"orderId":"ORD-001","channel":"balance"}」 | 「调用支付接口」 |
| R6 等待可量化 | 写明时长或轮询条件 | 「等待 5 秒后刷新页面」 | 「等待系统响应」 |
| R7 数据断言可执行 | 数据库断言写具体 SQL | 「执行 SELECT balance FROM account WHERE user_id='test_user_001'，期望结果集 balance=50.00」 | 「检查余额正确」 |

## 2. 预期结果断言规范

按验证对象选择断言模板，每步预期 = 断言对象 + 具体字段 + 具体值/状态：

| 断言类型 | 模板 | 示例 |
|---------|------|------|
| UI 断言 | 页面/元素 + 文案/状态 | 「订单详情页状态标签显示『已支付』」 |
| 接口断言 | 响应码 + 响应字段 + 值 | 「返回 HTTP 200，code 字段=0，data.orderId 非空」 |
| 数据断言 | 表 + 字段 + 值（含变更前后） | 「account 表 balance 字段由 100.00 变更为 50.00」 |
| 通知断言 | 渠道 + 接收方 + 消息字段 | 「站内信收到 1 条新消息，含订单号、金额、时间戳 3 个字段」 |
| 状态断言 | 对象 + 状态字段 + 状态值（含变更前后） | 「订单状态字段由 待支付 变更为 已支付」 |
| 无变化断言 | 字段 + 保持值 | 「库存字段保持 10 不变」 |

- 一条预期只断言一件事；多个独立断言拆为多条预期并对应拆分步骤（如步骤 3 查询余额、步骤 4 查询流水）。
- 错误场景必须断言：错误码/文案 + 数据不变项（如「返回错误码 30002 且余额字段保持 49.99 不变」）。

## 3. 前置条件与测试数据构造规范

- **前置条件**写「状态」而非「动作」：写「测试账号 test_user_001 已登录，可用余额=100.00」；不写「登录系统」。
- **测试数据**三要素：名称 + 具体值 + 构造方式。构造方式枚举：
  - `预置SQL`：如 `INSERT INTO account(user_id, balance) VALUES('test_user_001', 100.00)`
  - `API调用`：如 `调用 POST /account/recharge` 充值 100.00
  - `页面造数`：如 `登录后在充值页充值 100.00`
  - `预置脚本`：如 `执行 data_init.py --case=pay_001`
- 禁止写「任意值」「合法值」「测试数据若干」；每条数据必须可落地。

## 4. 优先级定级规则

| 优先级 | 定义 | 判定规则 |
|--------|------|---------|
| P0 | 核心流程阻断缺陷 | 主流程功能用例；资金/库存正确性用例；核心状态流转用例 |
| P1 | 重要功能缺陷 | 边界类用例；关键异常（重复提交/并发/回调超时）；权限类用例 |
| P2 | 一般缺陷 | 提示文案类；非关键异常（格式错/类型错）；兼容性；性能基线 |

- 按判定规则映射，禁止凭感觉定级；同一 TP 拆分的多个 TC 保持同一优先级。

## 5. 模块划分规则

- 按业务域划分（订单/支付/账户/商品），不按页面划分。
- 模块边界判定：TP 的 REQ 归属哪个业务域，用例即归哪个模块；1 个 REQ 跨域时以触发入口所在域为准并在备注声明。
- 模块名用 2~6 字名词短语，单次任务内模块名唯一。

## 6. 用例标题命名规范

格式：`验证<场景/条件>时<期望行为>`，动宾结构、含关键数据特征：

- 好例：「验证余额恰好等于订单金额时支付成功」「验证订单数量为 11 时提交失败并返回错误码 30003」
- 坏例：「余额支付测试」「边界值用例 3」

## 7. 拆分与合并规则

- 1 TP → 1 TC 为默认；满足以下任一条件时拆分为多个 TC（均回链同一 TP）：
  1. 步骤数 >15 步；
  2. 断言目标跨 ≥2 个页面或 ≥2 个接口且中间需重新登录/切换环境；
  3. 单用例执行时长 >30 分钟。
- 拆分时前置条件/测试数据按拆后范围裁剪，不得残留原 TP 全部数据。
- 禁止合并不同 TP 为一个 TC（保持追溯链唯一性）。

## 8. 禁词清单（质量门禁强制检查）

步骤/预期中出现以下表述即判定不合格：

- "校验通过/校验失败/校验正确" → 必须写明校验的字段、规则与结果值
- "提示合理/提示正确/有相应提示" → 必须写明文案或错误码
- "显示相关提示/相应信息/处理成功" → 必须写明具体内容
- "数据正确/功能正常" → 必须写明具体字段与值
- "任意值/合法值/测试数据若干" → 必须写具体值
- "执行 TC-xxx 后" → 违反用例独立性，必须改写为可构造的前置条件
