# 用例编写技能（testcase-generation）

## 一、技能定位

将测试点（TP）转化为**可直接交给测试人员执行的标准化用例**。每个用例：

- 步骤强可操作：每步 = 一个动作 + 一个对象 + 具体数据值；
- 预期可精确断言：每步预期 = 具体字段 + 具体值/状态/错误码；
- 数据可独立构造：前置条件与测试数据足以让执行者不依赖其他用例即可开始执行。

与相邻技能分工：

- 上游 `test-point-extraction`：产出 TP（验证什么、怎么断言、需要什么数据）。
- 本技能：将 TP 展开为「怎么一步步做」的可执行用例（TC）。
- 下游 `testcase-review` / `testcase-export`：评审与导出本技能产物。

## 二、编号契约（继承自全局约定）

| 前缀 | 含义 | 本技能行为 |
|------|------|-----------|
| TC-xxx | 用例 | 本技能产出，自 TC-001 起连续编号，禁止跳号 |
| TP-xxx | 测试点 | 沿用上游编号；每个 TC 必须回链 ≥1 个 TP |
| REQ-xxx / CL-xxx | 需求点/澄清问题 | 沿用上游编号，仅在追溯矩阵中引用 |

- 默认 1 个 TP 生成 1 个 TC；TP 步骤 >15 步或断言目标跨多个页面/接口时，拆分为多个 TC，各 TC 回链同一 TP。
- 依赖 CL 未确认规则的 TC，在备注标注「依赖 CL-xxx 确认后复核」。

## 三、工作流程

按以下 6 个阶段顺序执行。

### 阶段 1：输入识别

- **路径 A（标准）**：输入为测试点提取报告（TP 全表 + 覆盖矩阵） → 直接进入阶段 2。
- **路径 B（仅 TP）**：输入为裸 TP 清单（无 REQ 关联） → 先按 TP 名称补建模块映射与优先级，REQ 列填「—」，并在报告风险提示声明追溯链缺失。
- **路径 C（越级输入）**：输入为原始需求文档 → 不直接编写用例，输出提示：「请先执行 requirements-analysis 与 test-point-extraction 技能」，并在用户坚持时按快速基线路径执行且显著标注质量风险。

### 阶段 2：模块划分与编号规划

- 按 TP 的 REQ 关联关系划分模块；模块命名规则与边界判定见 `references/case-writing-rules.md` 第 5 节。
- 按模块对 TP 分组排序，规划 TC 编号段（如 订单模块 TC-001~TC-020），输出「模块×TC 编号段」规划表。

### 阶段 3：用例要素拆解（每个 TP → 用例骨架）

对每个 TP 产出用例骨架：

- **用例标题**：按 `references/case-writing-rules.md` 第 6 节命名规范生成；
- **优先级**：按 `references/case-writing-rules.md` 第 4 节定级规则映射（P0/P1/P2）；
- **用例类型**：沿用 TP 的测试类型（功能/边界/异常/状态流转/权限/并发/性能/兼容性/安全）；
- **前置条件**：将 TP 的「输入与前置状态」改写为可构造的状态描述（账号+数据状态+环境状态）；
- **测试数据**：将 TP 的「所需测试数据」具体化为 名称+具体值+构造方式（预置 SQL / API 调用 / 页面造数），禁止写"任意值"。

### 阶段 4：步骤与预期编写（核心阶段）

按 `references/case-writing-rules.md` 第 1、2 节规范编写：

1. 将 TP 的断言目标分解为「操作序列 + 验证序列」；
2. 每步只写一个动作：动词 + 对象 + 具体数据值（如「在数量输入框输入 11」），禁止"输入数据""进行校验"类空动作；
3. 步骤只写执行动作，系统自动行为一律写入对应预期（如"系统扣减余额"写在预期，不写在步骤）；
4. 预期结果与步骤编号一一对应，每步预期按断言规范写（UI 断言：元素+文案/状态；接口断言：方法+URL+响应码+响应字段；数据断言：表+字段+值；通知断言：渠道+接收方+消息字段）；
5. 涉及等待/轮询的步骤写明具体等待时长或轮询条件（如「等待 5 秒后刷新页面」）；
6. 接口调用类步骤写明 方法 + URL + 请求体字段与值（见模板示例）；
7. 数据库断言类步骤写明具体 SQL 与期望结果集。

### 阶段 5：质量门禁自检

按第 5 节逐项自检，不通过则修订：

- 可执行性：步骤无需任何额外信息即可执行；
- 断言精确性：命中禁词清单即不合格；
- 一致性：预期条数 = 步骤条数，编号一一对应；
- 独立性：用例不依赖其他用例的执行顺序；所需数据均在前置条件/测试数据中构造；
- 可追溯性：TC→TP→REQ 回链完整；
- 数据可构造性：每条测试数据均有构造方式。

### 阶段 6：输出

按第 4 节输出契约生成报告，对照 `templates/testcase-output-template.md` 检查字段完整性。

## 四、输出契约

### 4.1 用例全表（核心产物）

| 用例ID | 关联测试点 | 模块 | 用例标题 | 优先级 | 用例类型 | 前置条件 | 测试数据 | 测试步骤 | 预期结果 |
|--------|-----------|------|---------|--------|---------|---------|---------|---------|---------|

- 「测试步骤」与「预期结果」单元格内使用编号列表（1. 2. 3.），两步之间用 `<br>` 分隔；编号一一对应。
- 步骤与预期同编号必须对应同一动作/同一断言，禁止错位。

### 4.2 TP→TC 追溯矩阵

| 测试点ID | 用例ID | 备注 |
|---------|--------|------|

（1 对多时列出全部 TC；被拆分的 TP 在备注说明拆分原因。）

### 4.3 用例统计

| 模块 | 用例数 | P0 | P1 | P2 | 覆盖 TP 数 |
|------|--------|----|----|----|-----------|

### 4.4 报告结构

```
# 测试用例编写报告
## 1. 输入说明（路径 A/B/C）
## 2. 模块×TC 编号段规划表
## 3. 用例全表（TC）
## 4. TP→TC 追溯矩阵
## 5. 用例统计
## 6. 风险提示（依赖 CL 的用例、数据构造难点、环境依赖）
```

## 五、质量门禁（输出前逐项自检，不通过则修订后重新输出）

1. **可执行性**：每个步骤含 动词+对象+具体数据值；执行者不查任何文档即可执行。
2. **断言精确性**：沿用全局禁词清单（"校验通过""提示合理""显示相关提示""处理正确"等）；预期必须写具体字段+具体值/状态/错误码；命中禁词即不合格。
3. **一致性**：预期条数 = 步骤条数；步骤编号与预期编号一一对应；步骤中不夹带预期。
4. **独立性**：无「执行 TC-xxx 后再执行本用例」类依赖；前置条件与测试数据自包含。
5. **可追溯性**：每个 TC 回链 ≥1 个 TP；TP→TC 矩阵无孤儿 TP。
6. **数据可构造性**：每条测试数据有具体值与构造方式，无"任意值/合法值"。
7. **优先级合规**：优先级按定级规则映射，无凭感觉定级。

## 六、约束与禁止事项

- 只生成用例，不执行用例、不生成自动化脚本。
- 禁止修改上游 TP 的断言目标；发现 TP 本身有覆盖空洞或断言错误时，回写备注并建议回到 test-point-extraction 补点，不在用例层擅自扩范围。
- 用户提供用例模板/字段要求时，优先遵循用户格式；字段裁剪时保留 TC/TP/步骤/预期四要素的最低追溯链。
