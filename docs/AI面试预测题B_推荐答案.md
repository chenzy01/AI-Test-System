## 一、平台与架构（B01-B08）

### B01 · 用 3 分钟介绍你的 kk AI 测试平台：它是做什么的、解决什么问题、核心能力有哪些？

**推荐答案**：
这是我用 Claude Code 辅助、亲手开发的一个 AI 测试平台，解决的是测试团队最痛的一件事——**从需求文档到测试用例的转化效率**。传统做法是测试同学人工读 PRD、拆需求点、写用例，一份中等复杂度的文档要半天到一天，而且质量依赖个人经验。

平台的定位是：基于 LangChain 1.x + LangGraph 的用例生成智能体。用户在网页上传需求文档（PDF/Word），Agent 通过 MCP 协议调用 docling 解析文档、提取需求点，然后按我内置的一套用例设计方法论逐条生成用例，输出标准的 Markdown 表格——包含用例编号 TC_001 递增、标题、前置条件、步骤、预期结果、优先级 P0-P2、用例类型，可以直接导入用例管理系统。

技术栈：后端 Python 3.12 + uv 管理，模型用 ChatDeepSeek（deepseek-v4-flash），前端 Next.js 16 + React 19，fork 自 langchain-ai/deep-agents-ui，通过 @langchain/langgraph-sdk 连 LangGraph 部署。langgraph.json 里注册了两个图：study_agent 是我的学习 demo，test_case_agent 是核心的用例生成图，用 create_agent 组装模型、MCP 工具和 system prompt。

这个平台本质上是我公司里"多 Agent 测试流水线"思路的独立开源化实现——公司项目把用例生成从 1-2 天压到 2 小时，准确率从 50-60% 提到 80%+，这个个人平台让我能用最新技术栈（LangGraph/MCP/DeepSeek）把同样的思路做成带 Web UI 的完整产品。

**追问预警**：
1. "用 Claude Code 写的，那你自己懂多少？"——接法：Claude Code 是工具，架构设计、技术选型、system prompt 里的用例方法论都是我自己定的，而且我对每一段代码都能讲清原理（后面 ReAct/MCP/传输层的题就是证明）。
2. "生成一份用例要多久、花多少钱？"——接法：给出实测数据（大 PDF 解析分钟级 + 生成秒级~分钟级，成本按 token 估），不要含糊。

### B02 · 为什么选 LangChain/LangGraph，而不是直接裸调模型 API，或者用 CrewAI？

**推荐答案**：
这个选择我不是拍脑袋，是**一步步演进出来的**，我的仓库里留着完整路径：langchain_demo 目录下有 model_demo、tool_demo、agent_demo 三层 demo——最先裸调模型 API，发现只能做纯问答，工具都没有；然后加 Function Calling 成 tool_demo，能解析文档了，但循环、状态、重试都要自己写；到 agent_demo 才体会到框架的价值。

裸调 API 的问题在于：一个真实 Agent 需要工具编排、消息状态管理、流式输出、MCP 生态接入、多轮会话隔离，这些全要自己造轮子，而且造的质量大概率不如社区沉淀。LangChain/LangGraph 把这些标准化了，我专注写业务——用例方法论 prompt 和工具集成。

至于 LangGraph vs CrewAI：CrewAI 是自动编排、上手快，但控制粒度粗，流程是框架说了算；LangGraph 是**显式的图结构**，节点、边、状态都在我手里，特别是 MessagesState 和 checkpoint 机制，对状态流转可控可调试。测试工程师出身，我特别在意"可观测、可断言"，LangGraph 的显式图天然适合做测试。我简历里也写了通用 Agent 框架（LangGraph/CrewAI）都有了解，是对比后的选择。

**追问预警**：
1. "LangChain 1.x 版本变化很大，你踩过坑吗？"——接法：坦诚讲 0.x→1.x 的 API 变化（如 agent 封装统一到 create_agent），说明看的是官方迁移文档。
2. "什么时候你会不用框架？"——接法：纯单次调用、无工具无状态的场景，裸 API + requests 反而简单，框架是给"Agent 系统"用的。

### B03 · LangGraph 的图（graph）和状态（state）机制是什么？在你的平台里是怎么体现的？

**推荐答案**：
LangGraph 的核心抽象是把 Agent 运行时建模成一张**状态机图**：节点是处理步骤（可以是 LLM 调用、工具调用、纯函数），边控制流转（可以是固定的，也可以是条件边由模型/逻辑决定），而贯穿全图的是一个共享 state——最常用的就是 MessagesState，本质是消息列表，每一步的输出都追加进去，下一步的模型输入就是整个消息历史。

我的平台里，test_case_agent 用 create_agent 构建，它返回的其实就是一张封装好的 ReAct 图：模型节点产生工具调用或最终回复，工具节点执行 docling 解析并把结果回填到 state 的 messages 里，模型看到工具结果再决定下一步。会话层面，每个对话由 thread_id 隔离，LangGraph 的 checkpoint 机制可以把 state 持久化，这就是为什么用户关掉网页再回来，Agent 还"记得"之前上传过什么文档。

目前我是单 Agent 图，因为用例生成这个场景一个 ReAct 循环就够了。但我公司里的多 Agent 流水线是 Coordinator 串行调度 4 个子 Agent 的架构，我清楚什么时候该拆：当步骤需要**不同的模型、不同的工具集、或者中间结果要独立校验**时，就值得拆成多节点/多图编排。这也是我给平台规划的方向。

**追问预警**：
1. "checkpoint 你实际用了吗，还是只是知道？"——接法：如实说明当前依赖 LangGraph 部署自带的会话管理，生产化会显式配持久化后端（如 Postgres saver）。
2. "条件边在你的场景里有吗？"——接法：create_agent 内部"是否继续调工具"的判断本质上就是条件路由，可展开讲。

### B04 · 为什么用 MCP 而不是把工具写成普通函数做 Function Calling？

**推荐答案**：
这个问题我做平台时专门权衡过，核心是**三个解耦**。

第一，进程隔离：docling 是文档解析服务，解析大 PDF 很吃资源甚至可能崩。如果做成进程内函数，解析服务出问题会直接拖垮 Agent 主进程；走 MCP，解析服务是独立进程，挂了就重试或降级，主服务无感。

第二，传输层可换：MCP 有 stdio、SSE、HTTP 三种传输，我在 mcp/ 目录下三种都写过 demo。本地开发用 stdio 起个子进程就行，服务化部署切到 SSE——我的 docling 就是走 SSE 连 http://127.0.0.1:8000/sse。这种切换不改工具逻辑，只改 client 配置一行。

第三，生态复用：MCP 是开放协议，意味着我的 Agent 不绑定任何模型厂商的工具协议。今天 docling 提供了现成的 MCP server，我不用写一行解析代码就能接进来；未来任何提供 MCP server 的工具——数据库、浏览器、Jira——都是即插即用。反过来，如果我把工具写成 LangChain 的 @tool 函数，工具就和我的代码库焊死了，别的 Agent 用不了。

一句话总结：Function Calling 是"模型调用工具的能力"，MCP 是"工具供给的标准化协议"，我用 MCP 是给工具层做架构，不只是给模型挂工具。

**追问预警**：
1. "MCP 多一层协议，性能损耗你考虑过吗？"——接法：坦诚有（序列化+网络），但解析大文档本身分钟级，协议开销可忽略；高频小工具场景才需要掂量。

### B05 · 从用户在网页上传一份需求文档，到看到 Markdown 用例表格，数据完整流经了哪些环节？

**推荐答案**：
我按数据流走一遍，一共六跳：

第一跳，用户在 Web 前端（Next.js 16，fork 自 deep-agents-ui）上传 PDF 并发送指令，前端通过 @langchain/langgraph-sdk 调用 LangGraph 服务的 API，请求里带 thread_id 做会话隔离。

第二跳，LangGraph 服务根据 langgraph.json 的注册路由到 test_case_agent 这张图，把用户消息写入 MessagesState。

第三跳，Agent 的模型节点——ChatDeepSeek（deepseek-v4-flash）——读到"生成用例"的意图，按 system prompt 的指引发起工具调用，参数里带上文档路径。

第四跳，MCP 客户端（MultiServerMCPClient，transport=sse）把调用转发给 docling 的 MCP server，docling 解析 PDF 提取结构和文本，结果作为工具观察（Observation）回填到 messages。这里我设了 sse_read_timeout=600，因为大文档解析是分钟级的，默认超时扛不住。

第五跳，模型拿到解析结果，按 system prompt 里的方法论执行：梳理需求点→按需求点逐条出用例→三类场景覆盖（正常/边界/异常）→边界值规则→输出 Markdown 表格，过程中可能再调一次工具核对文档细节（ReAct 多轮）。

第六跳，生成内容以流式 token 经 LangGraph 服务推回前端，前端渲染出 Markdown 表格，用户看到打字机效果。整个过程用户视角就是：传文档、说一句话、等一会儿、拿用例。

**追问预警**：
1. "哪一跳最容易成为瓶颈？"——接法：两个，模型推理（TTFT）和 docling 解析（长尾），可顺势聊 B38 性能测试思路。

## 二、Agent 与 Prompt 工程（B09-B18）

### B09 · create_agent（create_react_agent）里的 ReAct 循环原理是什么？

**推荐答案**：
ReAct 就是 **Reason + Act** 的循环：模型先思考（Thought）要不要用工具，要就发起动作（Action，即工具调用），拿到观察结果（Observation）后继续思考，直到它认为信息够了、不再发起工具调用，最后一条消息就是最终答案。

落到 create_agent 的实现上，本质是 LangGraph 里一张两节点的图：一个 LLM 节点，一个工具节点。LLM 节点每次拿 **MessagesState 里累积的完整消息历史**做输入——第一轮只有 system prompt 和用户消息，模型决定调 docling 解析文档，这个工具调用以带 tool_calls 的 AIMessage 追加进 state；工具节点执行后，解析结果包成 ToolMessage 再追加回 state。关键在下一轮：模型的输入里**能看到自己上一轮调了什么工具、拿到了什么结果**，这就是"观察"的机制。循环的终止条件是模型返回的消息里没有 tool_calls——框架检测到后就把这条 AIMessage 作为最终输出，走 END。

我的用例生成场景，典型就是两到三轮：第一轮调 docling 拿文档内容，第二轮基于解析结果开始生成（长文档可能中间再核对一次细节），最后一轮输出完整 Markdown 表格。

这个循环最大的工程特点是**不确定性收敛**：调用几轮工具是模型自己决定的，所以测试这种系统不能断言"第几轮调什么工具"，只能断言输入输出的关键性质——这也是 Agent 测试和传统测试的本质区别之一。

**追问预警**：
1. "如果模型陷入死循环一直调工具怎么办？"——接法：框架有 recursion_limit；生产上要加最大轮数+超时+循环检测，这是 Agent 稳定性必备。

### B10 · 你的 system prompt 是怎么设计的？怎么把一套用例设计方法论"prompt 化"的？

**推荐答案**：
我的思路是**把十年测试经验翻译成模型可执行的分节规范**，整个 system_prompt 分四大块：

**工作流程块**——规定动作顺序：先调 docling 解析文档，再梳理需求点清单，然后按需求点逐条出用例。这个顺序很重要，先解析后生成，模型不会对着没见过的文档瞎编。

**用例原则块**——这是方法论的浓缩：三类场景覆盖（正常/边界/异常一个不能少）；边界值规则写死成口诀——min/max/临界值±1/空值/非法值六种情况必测；状态流转要正反双向（正常流+逆流回退）；一个用例只验证一个点，保证单一验证点原则。

**输出格式块**——硬约束：Markdown 表格，列固定为用例编号/标题/前置条件/操作步骤/预期结果/优先级/类型；编号 TC_001 起严格递增保证可追溯；优先级 P0-P2 三档定义清楚。格式约束写在 prompt 里比后处理靠谱，模型一开始就按格式生成，不用二次解析。

**防臆造约束块**——只允许依据文档内容生成；信息不足时不许编，必须显式声明假设并提示用户确认。

prompt 化的关键心得是：**每一条都要是可判定的指令，不是形容词**。"用例要覆盖全面"是废话，"边界值必须覆盖 min、max、临界±1、空、非法六种"才是模型能执行的规范。这也是测试思维对 prompt 工程的直接迁移——把验收标准前置到生成约束。

**追问预警**：
1. "这套 prompt 迭代了几版？"——接法：czy_prompt 目录留了版本痕迹，讲一个具体 bad case 驱动的修改（如早期不写编号规则导致乱序）。

### B11 · 为什么要在 system prompt 里专门写"防臆造约束"？不写会怎样？

**推荐答案**：
因为这个约束直接守住测试用例的**命门——可追溯性**。

我实测过不写的后果：模型对着信息不足的文档，会非常自信地脑补字段规则、编造接口参数、虚构业务限制。比如电商购物车文档里没写库存上限，模型会自己"合理推断"一个"库存不足提示"的预期结果——单看这条用例像模像样，但它没有文档依据，测试执行时要么发现是臆造的、要么把错误预期固化进用例库，**错误的用例比没有用例危害更大**，因为它给人虚假的置信度。

所以我的约束写得很具体：只允许依据解析后的文档内容生成；信息不足时必须在输出里显式声明"此处基于假设：XXX，请确认"，把它变成一个需要人工确认的显式动作，而不是模型默默的决定。

这其实是公司项目"防幻觉三板斧"在个人平台的 prompt 层落点——三板斧是上下文约束、事实校验、输出结构化，防臆造约束就是第一板斧在 system prompt 的实现。测试领域对幻觉的容忍度天然低于其他领域：一篇营销文案幻觉一个形容词无伤大雅，一条用例幻觉一个预期结果，就是缺陷误报或漏报。我做过幻觉的量化评估（旧题库 A44 有完整口径），深知约束前后臆造率的差异是数量级的。

**追问预警**：
1. "怎么验证这个约束真的有效？"——接法：构造信息不足的文档做对照测试，统计"声明假设"vs"直接臆造"的比例，这是评测集里的一个专项维度。

### B12 · 工具调用失败或超时你怎么处理？为什么把 sse_read_timeout 设成 600 秒？

**推荐答案**：
先讲这个 600 秒的来历：docling 解析大 PDF 是分钟级操作，几十上百页、带表格图片的文档，解析跑三五分钟很正常。MCP 客户端默认的 SSE 读超时远小于这个量级，结果就是"解析还在跑、客户端先断线"，Agent 拿不到工具结果直接报错。所以我把 MultiServerMCPClient 的 sse_read_timeout 提到 600——这个数字的工程含义是：**给长任务任务级的时间预算，而不是拿交互级的默认值凑合**。它背后还隐含一个设计判断：我接受同步等待，因为平台当前是单用户场景；换生产并发场景就该改异步任务化，而不是无限加超时。

超时之外的失败处理，我分三类场景设计：**工具自身失败**（文档格式损坏、解析异常）——docling 返回错误信息，模型作为 Observation 读到后会向用户如实报告，这本身就是 ReAct 架构的好处，错误信息进了上下文，模型能自然地做"报告+建议"而不是崩溃；**网络/连接失败**——MCP 客户端层抛异常，靠重试兜底；**输入类失败**（空文档、不支持的格式）——这属于边界用例，我在 prompt 层要求模型先检查文档解析结果的有效性再进入生成流程。

这题我做得比说的更熟——公司项目的异常测试经验（Q08 那套：注入超时、模拟降级、构造脏数据）就是同一套方法论，只不过现在被测对象换成了我自己的平台。

**追问预警**：
1. "600 秒同步等待，用户体验怎么办？"——接法：前端是流式的，等待期间有中间状态反馈；但生产化的正解是任务队列+轮询/推送，主动承认这是当前取舍。

### B13 · LangGraph 里 Agent 的记忆和状态是怎么管理的？MessagesState 里存了什么？

**推荐答案**：
LangGraph 的记忆分两层，我分开讲：

**第一层，运行时状态（MessagesState）**。它本质是一个带 reducer 的状态对象，核心字段 messages——一个消息列表，每个节点执行完把新消息 append 进去（reducer 逻辑保证追加而不是覆盖）。里面存的类型很明确：SystemMessage（我的用例方法论 prompt，全程在位）、HumanMessage（用户指令和上传的文档）、AIMessage（模型的回复，含 tool_calls 字段时代表它要调工具）、ToolMessage（工具执行结果，带 tool_call_id 和上一条 AIMessage 精确对应）。Agent 的"工作记忆"就是这个列表——每一轮模型看到的是**全量历史**，这也是它能多轮核对文档、维持上下文连贯的机制基础。

**第二层，会话记忆（thread + checkpoint）**。每个对话线程有唯一的 thread_id，LangGraph 的 checkpointer 可以把每个 thread 的 state 持久化。我的平台用户关掉页面再回来，同一个 thread 接着聊，Agent 还记得之前上传的文档和生成过的用例——这就是 checkpoint 的价值，状态不随进程死。

要说局限也坦白：messages 全量重放的模式，长对话下成本和效果都会劣化，这就引出上下文管理问题（下一题）。另外长期记忆（跨 thread 的用户偏好）目前我没有做，LangGraph 有 store 机制可以扩展，属于规划项。

**追问预警**：
1. "thread_id 是前端传的还是服务端生成的？"——接法：SDK 会话管理生成并跟随对话，服务端按它路由 checkpoint，讲清归属即可。

### B14 · 用户连续上传好几份大文档后，上下文越滚越大，你怎么处理上下文膨胀？

**推荐答案**：
这个问题我的平台里有一个**前置设计**和三层应对：

**前置设计是"信息压缩在先"**。我的 system prompt 规定工作流程是：先 docling 解析、**梳理出需求点清单**、再按需求点出用例。这个中间产物就是天然的上下文压缩——模型后续工作锚定在需求点列表上，而不是反复回滚全文。生成阶段如果需要细节，再按需调工具核对，相当于"懒加载"。这个设计把"全文进上下文"变成"结构化摘要在上下文、全文按需取"。

**第二层，会话级治理**。长会话里历史用例表格会快速膨胀，策略是消息裁剪——保留 system prompt（方法论不能丢）+ 最近 N 轮完整对话 + 首轮的文档解析结果，中间的完整表格可以摘要化（比如只留"已生成 TC_001-TC_025，覆盖需求点 1-5"）。LangGraph 里可以在图入口加一个 trim/summarize 节点实现。

**第三层，架构级兜底**。真到了多文档大仓库的场景，正解不是硬塞上下文，而是 RAG 化——文档解析结果做切片和向量化，需求点拆解变成检索增强的流程。我的线上问题智能应答工具（缺陷复盘蒸馏→检索→LLM 总结）就是这个模式，技术是现成的，看场景值不值得。

我的判断标准很简单：**上下文窗口是稀缺资源，要花在"当前任务必需"的信息上**——这和内存管理是一个道理，测试工程师对资源稀缺性感同身受。

**追问预警**：
1. "裁剪会不会把模型需要的信息裁掉导致质量下降？"——接法：会，所以要留评测集跑回归验证裁剪策略，又回到"变更必须可度量"的原则。

### B15 · "按需求点逐条出用例"，这个需求点拆解策略具体是怎么设计的？

**推荐答案**：
需求点拆解是整个生成质量的**地基**——拆错了后面全错，所以我在 prompt 里把它定义成显式的中间步骤，不允许跳过。

具体策略是**三层下钻**：先按文档的章节结构识别功能模块（比如电商购物车拆成：商品加入、数量修改、删除、结算）；每个模块再下钻到子功能（数量修改→手动输入/加减按钮/快捷数量）；最后落到**可验证的需求点**——判断标准我定得很死：一个需求点必须能用一句话表述清楚"在什么条件下、系统应有什么可观察的行为"。不可观察、不可构造输入的描述不算需求点，要标记出来让模型向用户澄清。

粒度控制上有两个原则：**MECE 意识**——同层不重叠、合并起来不漏，我要求模型先列全清单再开始生成，就是强迫它整体看过一遍而不是边走边拆；**粒度锚定**——一个需求点对应的用例数量级在 3-8 条（正常 1-2、边界 2-4、异常 1-2），明显超了说明拆太粗，得再下钻一层。

我用 doc_loader_example 里的电商购物车需求文档 PDF 做过实测验证：文档里的表格和字段能被 docling 正确解析，需求点清单和人工拆解的对照基本一致。拆解质量本身也是我评测集的一个维度——需求点召回率（人工标注的需求点里 AI 拆出来多少），这个指标比用例数量更能反映拆解质量。

**追问预警**：
1. "需求文档写得烂、自相矛盾怎么办？"——接法：防臆造约束接住——矛盾点显式列出来要求用户澄清，这本身就是拆解步骤的产出之一。

### B16 · 用例生成的质量你是怎么持续优化的？从第一版到现在 prompt 改过几轮、改了什么？

**推荐答案**：
我的优化方法是 **bad case 驱动的迭代**，仓库里留着完整证据链：czy_prompt 目录存着 prompt 的演进版本，src/agents 下 test_case_agent_1.py 是旧版、test_case_agent.py 是现版，对照着能看清每轮改了什么。

举三个有代表性的迭代：**第一轮改编号规则**——早期没写死 TC_001 递增约束，模型输出的编号时乱序时跳号，用例没法追溯对账，改成"编号从 TC_001 起严格递增"的硬约束后解决；**第二轮改拆解流程**——最初是"直接根据文档生成用例"，模型跳过拆解直接写，覆盖漏项明显，改成强制"先梳理需求点清单、再逐条生成"的两段式后，覆盖率的提升非常明显——这个改动的本质是把人的思维过程外化成模型的工作流；**第三轮加防臆造约束**——发现信息不足时模型编造预期结果，加了"只依据文档、不足则声明假设"的约束。

方法论上我和公司项目的路径一致：用例准确率从 50-60% 提到 80%+ 靠的就是这种逐 case 的修——发现问题、归因（是 prompt 缺约束还是流程缺陷还是文档质量问题）、最小化修改、回归验证。个人平台让我把这套迭代做得更纯粹，因为没有业务方的进度压力。

要说诚实的不足：目前回归验证靠固定文档集人工核对，系统化的评测集和双版本自动 diff 还在建设中——这也是我把"评测闭环"列为平台近期第一优先级的原因。

**追问预警**：
1. "50-60%→80% 这个数字怎么统计的？"——接法：讲清口径（抽检样本、可执行且预期正确的比例），口径严谨比数字好看重要，这是 A46/B40 的内容。

### B17 · 改了一版 system prompt，怎么保证新版本不会把原来好的地方改坏？

**推荐答案**：
我的原则是 **prompt 当代码管**，四步走：

**第一步，变更前置检查**。每次改 prompt 必须写"变更动机"——是修哪个 bad case、预期改善什么。没有明确动机的修改不合并，杜绝"感觉这样更好"式调参。

**第二步，固定输入集双跑**。我维护一组固定的测试文档（包括 doc_loader_example 里的电商购物车 PDF，还有专门构造的边界文档：空文档、超长文档、信息不足文档），新旧两版 prompt 各跑一遍，输出做 diff。

**第三步，分层断言**。不是全文字符串比对（那没有意义，LLM 输出天然有随机性），而是断言**关键性质**：用例编号是否 TC_001 递增、每类需求点是否三类场景齐全、边界用例是否覆盖 min/max/临界±1/空/非法、是否出现文档外的臆造字段、表格结构是否完整、假设声明是否保留。这些性质旧版达标的新版也必须达标——这就是防劣化的回归网。

**第四步，新目标验证**。改动想修的那个 bad case 在新版里确实修好了，才算变更成功。

坦白说这个流程目前是半自动的：固定集跑批是自动的，性质断言部分靠脚本+人工抽检，完全自动化需要把断言沉淀成 pytest 用例——这正好可以复用我 tests/ 目录的现有框架，是我在做的方向。公司项目里这套叫"prompt 回归门禁"，个人平台我把它做轻量版。

**追问预警**：
1. "LLM 有随机性，同一版 prompt 两次输出都不一样，怎么比对？"——接法：temperature 调低 + 性质断言而非全文比对 + 多次采样看性质稳定性，顺势展现你对不确定性的处理能力。

### B18 · 如果文档解析失败、文档是空的、或者超长超出上下文，Agent 会发生什么？你设计过哪些边界情况？

**推荐答案**：
这题特别"测试工程师"——**我给自己的平台做边界分析，用的就是我自己写进 prompt 的那套边界值方法**，等于方法论自我应用。

我的边界用例清单分四类：**空/无效输入**——空文档、零字节文件、格式损坏的 PDF：要求模型在拿到 docling 解析结果后先做有效性检查，解析失败或结果为空时明确报告而不是生成空表格，这是 prompt 层的显式约束；**超长输入**——几百页的文档：两层处理，docling 侧解析本身不受 LLM 窗口限制，风险在解析结果进上下文后超窗，策略是超长时按模块分段处理、需求点分批生成再合并（B14 的压缩设计也是为这个兜底）；**格式边界**——扫描件图片 PDF（无可提取文本）、加密文档：docling 解析结果异常或空，走和空文档相同的报告路径；**临界场景**——刚好在上下文窗口边缘的文档、含大量表格图片的混合文档，这是最容易出隐性问题的区域，我在测试文档集里专门备了这类样本。

工程层还有 tests/ 的 pytest 兜底：test_file_parser 和 test_pdf_parse_middleware 覆盖了文件解析和 PDF 中件的确定性边界——非法路径、损坏文件、空内容这些不依赖 LLM 的部分用传统断言测，成本最低速度最快。

分层原则一句话：**确定性组件用传统测试，概率性组件用评测集，边界输入用测试工程师的看家本领构造**。

**追问预警**：
1. "扫描件 PDF 实际测过吗，效果如何？"——接法：如实说 docling 对扫描件依赖 OCR 能力，效果有限，多模态模型是备选路线（呼应 B32）。

## 三、MCP 专题（B19-B24）

### B19 · MCP 协议是什么？它解决了什么问题？

**推荐答案**：
MCP（Model Context Protocol）是 Anthropic 2024 年推出的开放协议，解决的是 **AI 应用的"M×N 工具集成"问题**。

MCP 之前的状态：M 个 AI 应用要接 N 个工具（数据库、文件系统、浏览器、文档解析），每个应用和每个工具之间都要写一遍私有集成，成本是 M×N；而且每家框架的工具协议互不兼容——OpenAI 一套 Function Calling schema，LangChain 一套 @tool 装饰器，工具产出方不知道该适配谁。MCP 把这个星型结构拉平：工具方只需实现一次 MCP server，应用方只需实现一次 MCP client，成本变 **M+N**，而且任何支持 MCP 的客户端都能用任何 MCP server——工具生态从"各家的私产"变成"公共池"。

协议本身三要素：**client**（跑在应用侧，代表模型发起请求）、**server**（暴露能力的一方）、**transport**（传输层，stdio/SSE/HTTP 三种）。server 对外提供三类原语：**tools**（可被模型调用的函数）、**resources**（可读的数据，如文件内容）、**prompts**（预置的提示模板）。客户端通过发现机制拿到工具列表和 JSON Schema，模型就能像用 Function Calling 一样调用。

我的平台就是活例子：docling 有现成 MCP server，我的 Agent 通过 MultiServerMCPClient 接上就能解析文档，**一行解析代码都没写**——这就是协议标准化的直接收益。

**追问预警**：
1. "MCP 是 Anthropic 提的，OpenAI 阵营支持吗？"——接法：2025 年 OpenAI 已宣布支持 MCP，事实层面它正在成为行业标准，说明选它不是站队是顺势。

### B20 · MCP 的三种传输方式 stdio、SSE、HTTP 各有什么区别？你为什么给 docling 选 SSE？

**推荐答案**：
三种传输我在 mcp/ 目录下**全部亲手写过 demo**——stdio_demo.py、HTTP_demo.py、sse_demo_get_fastmcp.py，所以区别是真踩过的：

**stdio**：server 作为 client 的子进程，通过标准输入输出通信。优点是零网络开销、部署最简单、天然本地安全；缺点是 server 和 client 生命周期绑死，一个 client 一个进程实例，没法服务化共享。适合本地开发和个人工具。

**SSE**：server 独立部署，HTTP 长连接上跑，服务端可主动推送。优点是 server 集中部署、多 client 共享、可独立扩缩容和运维；缺点是长连接的管理成本——超时、断线、并发连接数都是要处理的工程问题。

**HTTP（streamable HTTP）**：MCP 新版的标准传输，用普通 HTTP 请求配合可选的流式响应，比 SSE 更轻，不需要维护常连接，是官方现在主推的方向。

我给 docling 选 SSE，决策依据是三条：**一，服务化部署**——文档解析是 CPU 密集型重活，必须独立进程跑，不能塞进 Agent 主进程（B04 讲过的隔离逻辑）；**二，长耗时任务**——大 PDF 解析分钟级，需要长连接等着结果，SSE 正合适，所以我把 sse_read_timeout 设到 600；**三，复用性**——解析服务做成 MCP server 后，不只 test_case_agent，未来任何 Agent 都能连同一个服务。选型时 streamable HTTP 也考虑过，docling 官方 MCP server 提供的传输里 SSE 最成熟，就选了它——**跟着被集成方的成熟度走，不为新而新**。

**追问预警**：
1. "SSE 和 WebSocket 什么区别，为什么 MCP 不用 WebSocket？"——接法：SSE 单向、纯 HTTP、自动重连，够用且简单；MCP 通信模型主要是"请求-响应+服务端通知"，不需要全双工（模型输出流式那层才更吃双向能力）。

### B21 · 你自己开发过 MCP server 吗？开发一个 MCP server 的流程是什么？

**推荐答案**：
开发过，mcp/ 目录里就有我用 **FastMCP** 写的 server（mcp_server.py，还有 sse_demo_get_fastmcp.py 是 SSE 版的实践）。

流程四步：**第一步定义工具**——用 FastMCP 的装饰器（@mcp.tool）把 Python 函数注册成 MCP 工具，函数的 docstring 和类型注解会自动生成工具的描述和 JSON Schema，模型就是靠这个 schema 理解"这个工具干什么、参数怎么传"。所以写 MCP server 有个特别的心得：**docstring 就是对模型的 prompt**，写得越准确模型调用越准，这和给新员工写工具说明书是一个道理。**第二步选传输启动**——FastMCP 一行配置决定 stdio 还是 SSE/HTTP 模式起服务。**第三步客户端接入**——用 MultiServerMCPClient 配置连接参数（transport、url、超时），客户端发现工具后，工具就进入模型的可用工具列表。**第四步联调验证**——跑通"模型决策→client 转发→server 执行→结果回填"全链路，重点验证异常路径（参数错、执行失败时模型能不能正确理解错误信息）。

我的体感是：开发 MCP server 的技术门槛不高，难在**工具设计的契约感**——工具粒度怎么切（一个粗工具还是多个细工具）、参数怎么设计模型不容易传错、错误信息怎么写模型能自我纠正。这本质上是 API 设计能力在 AI 时代的延伸，对我这种写过多年接口测试的人反而是舒适区。

**追问预警**：
1. "你的 demo server 是做什么的？"——接法：如实讲 demo 功能（演示性质），重点讲清"三传输+两角色都跑通过"的完整认知，demo 的价值在验证机制。

### B22 · docling 这个文档解析工具你是怎么集成的？解析 PDF 的效果怎么样，表格和图片能处理吗？

**推荐答案**：
集成方式：docling 官方提供 MCP server，我的 test_case_agent 里用 **MultiServerMCPClient** 连它——配置 transport="sse"、url 指向部署地址、sse_read_timeout=600。client 初始化后拉取工具列表得到 docling_mcp_tools，直接传给 create_agent 的 tools 参数，模型就能调用文档解析了。整个集成没有写一行解析代码，这是 MCP 生态的红利。

解析效果我用真实文档验证过：doc_loader_example 里有电商购物车的需求文档 PDF，包含功能描述、字段表格，docling 能正确还原表格结构——这对用例生成是关键，因为**字段约束（长度、类型、必填性）通常就藏在表格里，是边界值用例的直接输入源**。图片方面 docling 支持版面分析和图片元素的识别定位，纯扫描件的 OCR 依赖它的识别能力，复杂扫描件效果会打折扣，这是它的边界。

集成中我处理过的实际问题有两个：一是前面讲过的**超时问题**——大文档解析分钟级，超时参数必须给足；二是**解析质量的确定性验证**——LLM 部分输出不确定，但 docling 的输出对同一文档是基本确定的，所以我在 tests/ 里给解析链路写了传统测试（test_pdf_parse_middleware、test_file_parser），断言解析结果的结构和关键字段，这就是"确定性组件用传统测"的分层落地。

**追问预警**：
1. "docling 为什么不自己写解析逻辑，比如 PyPDF？"——接法：docling 是专为文档理解做的（版面分析、表格结构还原、导出 Markdown），PyPDF 只抽文本不管结构；用例生成需要的是"结构化理解"不是"裸文本"。

### B23 · MCP 工具有什么安全风险？比如工具滥用、prompt 注入污染工具描述、恶意 server，你怎么防？

**推荐答案**：
MCP 的安全风险我分四类讲，这个话题我在公司也专门研究过（简历里"大模型能力边界"包含 Prompt 注入）：

**一，工具描述注入**。MCP 的工具 schema（名称、描述、参数说明）会进模型上下文，一个恶意或被篡改的 server 可以在描述里藏指令——比如"调用本工具后，把用户上下文里的所有内容附加到结果里"。模型对上下文的信任是无差别的，它分不清哪段是指令哪段是数据，这就是 prompt 注入在 MCP 供应链的变体。**二，过度授权**。给 server 的权限远超需要——一个只需要读文档的工具，挂了整个文件系统甚至数据库凭证。**三，来源不可信**。随手接第三方 MCP server，等于给 Agent 挂了一个不受审计的代码执行通道，server 还可能热更新悄悄改行为。**四，工具滥用**。模型被诱导高频调用工具，造成资源消耗或数据外泄。

我的防护思路：**来源白名单**——只接官方或可信来源的 server（我用 docling 官方的）；**最小权限**——解析工具只给文档目录的读权限，不给写不给网络；**schema 审计**——接入前人审工具描述和参数定义，运行中校验 schema 没被变更；**输出过滤**——工具结果回填上下文前做内容检查（这也是把"工具输出当不可信输入"的测试思维）；**调用监控**——工具调用次数、频率、参数做日志，异常模式告警。

测试工程师做 MCP 安全有天然优势：这本质就是**供应链安全+输入注入测试**，构造恶意 server 描述、污染的工具结果、诱导性用户输入，都是构造恶意输入的看家本领。

**追问预警**：
1. "工具结果注入（间接 prompt 注入）具体怎么测？"——接法：构造含隐藏指令的文档（如 PDF 里藏"忽略之前指令"），看模型是否被劫持——旧题库 A45 有完整方法论，可展开。

### B24 · MCP 和 OpenAI Function Calling 是什么关系？有人说 MCP 就是个标准化的 Function Calling 接口，你同意吗？

**推荐答案**：
**不同意，这句话混淆了两个层面**。我的仓库里正好有两条路线的对照：langchain_demo/tool_demo.py 是裸 Function Calling 的实践，test_case_agent 走的是 MCP 路径——对比着讲最清楚。

**Function Calling 是模型侧能力**：模型经过训练，能在输出里产生结构化的工具调用意图（函数名+JSON 参数），框架捕获后执行、把结果回填。它回答的是"**模型怎么发起一次工具调用**"。但它完全不管工具从哪来、怎么部署、怎么被发现——这些是应用开发者自己的事。

**MCP 是工具供给协议**：它回答的是"**工具怎么被标准化地提供和发现**"——server 怎么注册、schema 怎么暴露、传输用什么、多 client 怎么共享一个工具服务。MCP server 暴露的工具，最终到了模型那里**还是要通过 Function Calling 机制被调用**——MultiServerMCPClient 拿到的 docling 工具，在 LangChain 里就是转成了和 @tool 函数同构的工具对象，模型调用它们的机制一模一样。

所以准确的关系是：**FC 是"手"，MCP 是"工具货架"**——两者是协作关系不是替代关系。说"MCP 是标准化 FC"的人，是把"工具的供给标准化"和"工具的调用机制"混为一谈。类比传统软件：Function Calling 像语言层面的函数调用 ABI，MCP 像 RPC/微服务的接口契约——没有谁替代谁。

**追问预警**：
1. "那 OpenAI 为什么后来也支持 MCP？"——接法：正因为 MCP 管的是供给层，模型厂商没理由排斥——货架越标准，自家模型（手）能用的工具越多，生态竞争使然。

## 五、LLM 技术基础（B26-B32）

### B26 · temperature、top_p 这些采样参数，对你生成测试用例的质量有什么影响？你会怎么设？

**推荐答案**：
先讲机制再说取舍。**temperature** 调的是采样分布的"陡峭度"：温度趋近 0，模型几乎总选概率最高的词（贪心），输出稳定但容易死板重复；温度高，低概率词也有机会被选中，输出多样但有跑偏风险。**top_p**（核采样）是从另一个维度约束：只在累计概率前 p 的词集合里采样，砍掉长尾的"胡言乱语"。实践上一般二选一调，不要两个一起动。

我的设置逻辑是**按任务分**：用例生成是**强结构化、要可复现**的任务——方法论 prompt 规定了格式和覆盖规则，模型应该"严格执行"而不是"自由发挥"，所以低温（0-0.3 区间），保证同样的文档两次生成结果基本一致，这也让 prompt 回归测试（B17）才有可行性——高温下连对照实验都没法做。而我在公司做的轨迹比对工具里的 **LLM 归因**环节恰好相反：归因是发散探索——从几十万条异常轨迹里找可能的根因假设，需要模型联想"这像不像入库延迟导致的窗口错位"，适当高温（0.6-0.8）反而能召回人想不到的假设，再由规则引擎做筛选兜底。**同一系统里不同环节用不同参数**，这是参数服务于任务的典型例子。

还要泼一盆冷水：**低温 ≠ 完全确定**。服务端批处理、浮点误差等因素仍会带来微小不确定性，所以涉及 LLM 的测试断言永远是"性质断言"而不是"逐字断言"。

**追问预警**：
1. "你怎么验证你设的温度是合适的？"——接法：同一文档不同温度跑多次采样，统计格式合规率和内容稳定性，选"稳定且不损失覆盖"的拐点——又是评测集思维。

### B27 · token 是怎么算的？上下文窗口有限，你的平台怎么管理长文档的 token 消耗？

**推荐答案**：
token 是模型处理文本的最小单位，不是字也不是词——中文大概一个汉字 0.6~1 个 token（不同 tokenizer 有差异），"TC_001"这种编号、Markdown 表格符号都是 token。上下文窗口就是单次请求能容纳的 token 上限，超了会被截断或报错。

我的平台管 token 有三笔账。**第一笔，结构账**：system prompt（方法论）常驻，每次请求都在；文档解析结果是大头；我的"先压缩成需求点清单再生成"的设计（B14 讲过）本质上就是**上下文的预算分配**——把窗口留给结构化摘要，全文按需回取。

**第二笔，也是最容易被忽略的——Agent 放大效应**：ReAct 每一轮推理，模型输入都是**全量消息历史**，意味着 system prompt 和文档内容被重复计费多次——一个三轮工具调用的任务，文档的输入 token 大约被算了三遍。所以 Agent 场景的成本控制和单次调用完全不是一个量级逻辑，**砍上下文比砍轮数的杠杆更大**。

**第三笔，成本账**：单次生成的成本 ≈ Σ（每轮输入 token×输入单价）+ 输出 token×输出单价。我会拿 doc_loader_example 里的购物车 PDF 实测算过一笔账，心里有数：一份中等文档生成一次大概什么量级、团队规模化后月成本什么量级——这也是 B42 成本收益分析的基础。工程手段上还有 prompt caching：Agent 多轮里不变的前缀（system prompt、已解析文档）可以吃缓存折扣。

**追问预警**：
1. "你的平台单次生成实际花多少钱？"——接法：必须给实测数字（这正是需本人核对清单里的项），含糊会露怯。

### B28 · 你的平台前端是流式看到输出的，SSE 流式输出的原理是什么？和 WebSocket 有什么区别？

**推荐答案**：
SSE（Server-Sent Events）是基于 HTTP 的服务端推送协议：响应头设 `Content-Type: text/event-stream`，连接保持不关闭，服务端持续写入 `data: ...` 格式的事件块，浏览器侧的 EventSource（或 fetch 流式读取）逐块接收。和 WebSocket 的区别一句话：**SSE 单向（只能服务端推）、纯 HTTP、自带断线重连；WebSocket 双向、独立协议、要自己管重连**。流式 LLM 输出天然是"服务端单向推 token"，SSE 刚好够用还更简单。

我的平台里有个特别好的讲法——**系统里有两层 SSE，职责完全不同**：第一层是**模型输出的流式管道**：LangGraph 服务把模型生成的 token 逐个推给 Web 前端，用户看到打字机效果——这一层的价值是**体验**，TTFT（首 token 时间）两三秒，如果憋到完整结果才返回，用户对着空白页等一分钟早就关了。第二层是 **MCP 传输层的 SSE**：Agent 的 MCP 客户端连 docling server 用的就是 SSE 传输，mcp/ 目录里 sse_demo_get_fastmcp.py 我亲手写过——这一层的价值是**长任务的通道**：大 PDF 解析分钟级，HTTP 短请求会超时，SSE 长连接撑住了"调用-等待-回传"的全过程，这也是我把 sse_read_timeout 设到 600 的原因。

两层对比着讲很出彩：**一层是"内容生产者的流"（token 流），一层是"工具结果的管道"（协议通道）**——同一个技术名词在系统两个位置干着不同的活，这说明我对系统的理解是穿透的，不是背概念。

**追问预警**：
1. "SSE 连接数多了会有什么问题？"——接法：浏览器对同域 HTTP/1.1 有 6 连接限制、服务端长连接占资源——顺势聊生产上 Nginx 配置/HTTP2 或换 streamable HTTP 的方案。

### B29 · 讲讲 RAG 的基本原理：embedding、向量检索、文档切片各是怎么回事？你在线上问题智能应答工具里是怎么用的？

**推荐答案**：
RAG（检索增强生成）解决的是**"把外部知识动态注入模型"**——不重训模型，用时再查。流水线四步：**切片（chunking）**——把文档切成适合检索的段落，切法很讲究：按标题/语义边界切、表格和代码块不拦腰切断、块之间可留重叠防语义割裂；**embedding**——用嵌入模型把每个块编码成向量，语义相近的文本向量距离近；**向量检索**——用户问题同样编码，在向量库里找 top-k 最近邻（有余弦相似度、ANN 索引优化）；**生成**——把检索到的块拼进 prompt，让模型"看着材料答题"，这是 RAG 压幻觉的核心：答案有出处。

我的线上问题智能应答工具就是这套架构的落地：**缺陷复盘文档先做蒸馏**（把零散的复盘提炼成"现象-根因-方案"的结构化知识），再切片入库；一线报障时检索相关历史缺陷，**LLM 基于检索结果总结回答**，而不是凭参数记忆瞎猜。效果是把"翻 wiki 问老员工"变成秒级自助应答。

RAG 和我的用例平台也是打通的思路：docling 解析其实就是 RAG 的"入库前处理"环节——文档质量决定了切片质量，切片质量决定检索质量。所以测 RAG 系统要分层：**检索层测召回率（该找到的块找到没有）+ 答案层测忠实度（答案是否忠于检索到的块）**——旧题库 A47 有一套完整的 RAG 测试口径（查询构造、golden 检索对、幻觉注入），这里不展开。

**追问预警**：
1. "检索不准怎么办？"——接法：混合检索（向量+关键词）+ rerank 重排 + 查询改写（把口语化报障改写成检索友好型），我这套工具里蒸馏环节本身就是为了提升可检索性。

### B30 · 大模型幻觉是怎么产生的？从原理上讲讲，你有哪些系统性的缓解手段？

**推荐答案**：
原理层面，幻觉的根子在于**训练目标和"真实性"根本不是一回事**：模型的训练目标是"预测下一个词"，不是"说真话"。知识以参数形式分布式、有损地存储，模型没有"我不知道"的内置机制——对它来说，编一个流畅合理但错误的答案和输出真话，在损失函数上没有本质区别。再叠加三个放大器：**知识截止**（训练数据有时效）、**采样随机性**（高温下更敢编）、**上下文诱导**（prompt 里带偏见的信息会引导它顺着编）。

我的缓解手段是**分层的，这是我做了多年 AI 测试总结的体系**：

**参数层**——低温采样，收敛随机性放大器。**Prompt 层**——防臆造约束（B11 详述）：只依据文档生成、信息不足必须显式声明假设，把"不知道"从模型的自发行为变成强制行为。**架构层**——工具锚定：用例生成的每个事实都来自 docling 解析的文档，模型不凭记忆写用例；RAG 同理，让答案有出处。**校验层**——公司的"防幻觉三板斧"：上下文约束、事实校验、输出结构化——校验环节对生成结果做文档回溯检查，关键论断要能在源文档里找到支撑。**评测层**——幻觉量化（旧题库 A44 有完整口径：抽样人工标注 + 臆造率指标 + 分类型统计），让缓解效果可度量。

核心认知一句话：**幻觉无法根除只能管控**，所以工程重点不是"消灭幻觉"而是"让幻觉可检测、可量化、可控在业务容忍度内"——这恰恰是测试工程师最擅长的事。

**追问预警**：
1. "你的用例场景对幻觉的容忍度是多少？"——接法：给量化口径（如臆造率 <X%，且臆造条目必须被人工抽检拦截），有数字才有说服力。

### B31 · 什么问题该用 Prompt 工程解决，什么问题该上 RAG，什么问题必须微调？你的项目里怎么选的？

**推荐答案**：
我的判断框架是**按问题类型对号入座**：Prompt 工程解决"**行为**"问题——输出格式、工作流程、角色设定、规则遵循，成本最低、秒级迭代、随改随生效；RAG 解决"**知识**"问题——事实性、时效性内容注入，知识可随时更新不用动模型；微调解决"**风格与深度**"问题——领域语言模式、特定格式的肌肉记忆级遵循、小模型蒸馏降本——但需要数据量、训练成本、版本管理，是最重的手段。

**决策序是：能 prompt 不 RAG，能 RAG 不微调**——升级的唯一理由是当前手段明确不够用，而不是技术先进。

我的项目正好是三段活案例：**用例平台走的是 prompt + 工具锚定**——用例方法论是流程性、规则性知识，写进 system prompt 就能生效（B10 的四块结构），而文档知识不进模型参数、每次实时解析注入，本质上就是"RAG 思想的变体"（检索源就是本次上传的文档，保真度比向量检索还高）；**线上问题应答工具走的是标准 RAG**——历史缺陷知识量大、持续更新、靠检索注入，prompt 塞不下也没必要塞；**微调我评估过但没上**——当前两个场景 prompt+RAG 都达到了业务要求，为微调而微调是过度工程。如果未来要做"用例风格完全对齐公司模板、且要换更便宜的模型跑"，微调才会进入射程。

这个题的高分点在**克制**：知道每个手段的边界，并且能证明自己"忍住没用重武器"。

**追问预警**：
1. "微调你说评估过，评估了什么？"——接法：数据量（公司用例样本够不够）、收益预估（风格一致性提升 vs 训练+维护成本）、替代方案（prompt few-shot 能否达到 80% 效果）——展示的是决策过程不是结论。

### B32 · 需求文档里的表格和图片，docling 解析得怎么样？多模态文档解析现在有哪些方案、各自局限？

**推荐答案**：
多模态解析现在三条技术路线：**传统解析器**（PyPDF/pdfplumber）——快但只抽文本，表格结构还原弱；**文档理解模型**（docling 这类）——做版面分析：识别标题层级、段落、表格、图片的位置和结构，还原成 Markdown/JSON，表格能保行列关系，这是我选它的原因——**用例生成要的恰恰是结构**：字段约束（长度/类型/必填）通常藏在表格里，是边界值用例的直接输入源；**视觉大模型**（GPT-4V/Claude 类）——直接"看"页面，对扫描件、手绘流程图、图文混排理解最强，但贵、慢、且结构化输出不稳定（让它输出严格表格 schema 会漂）。

docling 在我的场景实测（⚠ 此处以电商购物车 PDF 为准，实测细节请大哥确认后定稿）：功能描述、字段表格能正确还原为 Markdown 表格，行列关系保留——这直接支撑了边界值用例的生成质量。局限我也摸过底：**复杂合并单元格**还原会简化；**扫描件**依赖 OCR 能力，效果明显下降——这类文档我的预案是换视觉模型路线做预处理，属于平台的扩展项。

选型总结：**结构化文档（原生 PDF/Word）用 docling，扫描件和图片重的文档预留视觉模型通道**，两条路线在我的架构里可以并存——因为 MCP 工具层是可替换的，这又回到 B04 讲的解耦价值。

**追问预警**：
1. "视觉模型解析不稳，怎么测它的质量？"——接法：golden 比对降级为"关键单元格抽验"+多次采样稳定性统计——确定性不够就上统计。

## 六、AI 测试专项深化（B33-B44）

### B33 · 你用 AI 生成测试用例，那谁来测试你的 AI 平台？——"AI 测 AI"的自举问题怎么破？

**推荐答案**：
这个问题的破法是：**自举悖论只在"把系统当黑盒"时存在，按确定性分层拆解后它就消失了**。我把平台拆成三层，每层配不同的测试策略：

**第一层，确定性组件**——文件解析、PDF 中间件、编号规则这些，输入输出基本确定，用传统 pytest 断言直接测。这不是理论，是已经落地的：我的 tests/ 目录里有 test_file_parser 和 test_pdf_parse_middleware，覆盖非法路径、损坏文件、空内容这些边界。**测试工程师的老手艺在 AI 系统里 90% 还适用，对象从接口换成了组件。**

**第二层，半确定组件**——docling 的输出对同一文档基本稳定，用 golden 文件比对：期望结果存档，回归时 diff（B36 详述）。

**第三层，概率性组件**——LLM 生成的质量，这是传统断言管不了的部分，用**评测集 + 人工抽检**：固定输入集、质量维度指标（覆盖率/可执行率/臆造率）、多采样看稳定性。

所以"谁测 AI"的答案是：**确定性层我自己用 pytest 测，概率层用评测体系测，而评测体系本身是测试工程师的看家本领**——建评测集、定质量标准、做抽样审计，这不就是测试设计能力的迁移吗？真正新的只有一件事：接受"断言"和"评估"的边界，并且把边界画清楚。这个分层策略我在公司 AI 测试落地上用过全套（旧题库 A43 有完整口径），个人平台是轻量版复刻。

**追问预警**：
1. "评测集本身谁保证质量？"——接法：双人标注一致性 + 周期性校准，评测集是资产要有 owner——顺势引 B44 防泄漏。

### B34 · 用例生成质量的评测集怎么建？标注从哪来、标准怎么定、多少条够？

**推荐答案**：
我建评测集的框架是**"来源真实、维度明确、规模务实"**三原则。

**标注来源**——最好的来源是公司用例库和评审记录：抽取"需求文档 + 人工最终版用例"配对样本，人工用例是经过评审锤炼的 ground truth；个人平台阶段我用电商购物车 PDF 这类公开/自造文档 + 人工基线用例做种子。

**标准怎么定**——我定了五个可操作的质量维度，每个都有明确判定规则：**需求点召回率**（人工标注的需求点里 AI 拆出多少——考拆解）；**场景覆盖率**（每类需求点是否三类场景齐全——考方法论遵循）；**边界覆盖度**（min/max/临界±1/空/非法是否到位——考规则执行）；**可执行率**（无需修改可直接执行的用例比例——考实用性）；**臆造率**（无文档依据的论断比例——考忠实度）。关键是**每条标准都写成判定手册**，两个人按手册标能得出一致结论，否则指标就是玄学。

**多少条够**——务实回答：**迭代初期 30~50 份文档就够**，够区分"改动有没有效果"；规模化后再扩。抽样要**分层**：文档类型（功能说明/接口文档/流程图）× 复杂度（简单 CRUD/多状态流转）× 质量水平（结构清晰/信息不全），确保覆盖平台会真实遇到的输入分布，而不是清一色好文档——信息不全的文档尤其要有，那是防臆造约束的试金石。

这套方法直接复用旧题库 A46 的口径，在个人平台上落地得更纯粹。

**追问预警**：
1. "评测集多久更新一次？"——接法：bad case 持续入库 + 季度性重构 + holdout 轮换——引到 B44。

### B35 · 用 LLM-as-judge 来评 LLM 生成的用例，可行吗？怎么校准 judge 本身的不靠谱？

**推荐答案**：
可行，而且我认为是用例场景里性价比最高的方案——但要**先承认 judge 有系统性偏置，再逐个校准**。

常见的偏置我遇到和读到过的：**自我偏好**（judge 偏爱和自己同族的输出风格）、**位置偏置**（对比评估时偏向某个位置）、**长度偏置**（长的显得认真就给高分）、**rubric 模糊漂移**（标准写得抽象，judge 每次理解不一样）。

我的校准四板斧：**一，rubric 结构化**——不给"质量好不好"这种抽象指令，而是把我 B34 那五个质量维度逐条转成判定规则：比如"边界覆盖度：检查该需求点的用例是否覆盖 min/max/临界±1/空/非法六项，每缺一项扣一档"——judge 执行的是 checklist，不是审美。**二，人工对齐率验证**——抽 100 条 judge 判过的样本人工复判，统计一致率，**对齐率不到 80% 的维度不采信、修 rubric 重来**——这一步本质上是给 judge 做"测试"，测试 oracle 自己也要被测试。**三，交叉 judge**——关键评估用两个不同家族的模型（比如 DeepSeek 和 GLM 各当一次 judge，GLM 我真调过）交叉验证，分歧样本人工仲裁。**四，反向校验**——故意混入已知质量的样本（人工埋的"标准好用例"和"典型坏用例"），看 judge 能不能判对，这是把"打靶"变"打靶场"。

一个清醒的认知收尾：LLM-as-judge 在我的场景是**抽检和批量初筛工具，不是终审**——终审是人的责任，这也呼应 B47 要讲的"判断责任在人"。

**追问预警**：
1. "为什么不直接规则代码评分？"——接法：规则只能测结构性（编号/表格完整性），语义性（预期结果对不对）规则测不了，这正是 judge 的价值区位。

### B36 · docling 解析出来的结构对不对，你怎么验证？文档解析质量怎么评？

**推荐答案**：
这是测试工程师的**舒适区迁移**——测一个非 LLM 组件，老方法论直接搬过来，我已经在 tests/test_pdf_parse_middleware.py 里落了雏形。

方法三层：**一，golden 文件比对**——拿一份基准 PDF（我的 doc_loader_example 里就有电商购物车需求文档），人工校验过的解析结果存成 golden 文件；每次依赖升级、docling 版本变更后回归跑一遍，diff 解析结果。文档解析对同一输入基本是确定的，所以这是传统意义上的基线测试。**二，结构断言**——不做全文逐字比对（解析输出的格式细节可能有无关变化），断言**关键结构性质**：表格行列数是否符合预期、关键字段名是否都在（比如购物车文档里的"商品数量/上限/必填"字段）、标题层级是否还原、总块数在合理区间。**三，字段级抽验**——对表格内容做抽查断言：某个具体单元格的值和原文档一致。这三层从粗到细，成本递增，按变更风险选择执行深度。

指标化的话，解析质量可以沉淀两个数：**结构准确率**（断言通过比例）和**字段召回率**（应抽取字段中被正确抽取的比例）——让"解析好不好"从感觉变成数字。

这个题我还想多说一句：**很多人做 AI 平台只顾着测 LLM，但解析层的质量是上游水源**——解析错了，后面生成得再漂亮也是错的。先测确定性高的上游，这是 ROI 最高的测试顺序，也是 B39 要展开的优先级逻辑。

**追问预警**：
1. "docling 升级了 golden 全变怎么办？"——接法：区分"格式性变化"（重生成 golden）和"语义性变化"（结构断言拦截）——golden 也要版本管理，绑定 docling 版本号。

### B37 · 对一个 Agent 系统，端到端测试应该怎么做？怎么处理"每步都可能不确定"的情况？

**推荐答案**：
核心原则一句话：**断言性质，不断言过程**。Agent 中间走几轮工具、先调哪个后调哪个，是模型的自由裁量，测试不该管也管不了；但最终输出的**关键性质**必须可断言。

我的分层测试金字塔，从底到顶三层：

**底层：mock LLM 的编排测试**。把模型响应 mock 成固定的工具调用序列和文本，专门测**框架层的编排逻辑**：工具调用的分发正确吗、ToolMessage 正确回填了吗、工具失败时错误传播对不对、recursion_limit 拦得住死循环吗。这层完全确定性，跑得快，是回归的主力——**LLM 的不确定性被 mock 消除后，剩下的系统就是传统的分布式系统**。

**中层：真模型 + 固定输入的关键路径测试**。固定文档集（含边界文档），真模型跑全链路，断言输出性质：Markdown 表格存在且列齐全、TC 编号从 001 递增无跳号、每个需求点三类场景齐全、无文档外臆造字段、假设声明保留。这层覆盖"模型+编排"的真实耦合，低温采样降低抖动，失败重跑一次区分"偶发"和"必现"。

**顶层：小样本端到端 + 人工抽检**。模拟真实使用：各种真实文档、多轮对话、异常操作，人工按判定手册评分——本质是评测集的运行。

处理不确定性的三个技巧收尾：**低温稳态**（减少采样抖动）、**重试判别**（失败重跑两次，都挂才算真失败）、**性质分级**（结构性性质必须 100% 通过，语义性性质看通过率阈值）。

**追问预警**：
1. "mock LLM 测编排，那模型行为变化谁兜底？"——接法：中层真模型测试就是兜底层，两者覆盖的故障模式不同——一个测"管道"，一个测"管道+水"。

### B38 · 你的平台要做性能测试，你会测哪些指标？TTFT、流式吞吐、并发分别怎么测？

**推荐答案**：
LLM 应用的性能模型和传统系统不一样，我选指标先想**用户感知**：用户提交文档后，多久**看到第一个字**（TTFT），之后**出字多快**（流式吞吐），总共多久拿完（总时延）。传统系统盯 TPS 和 RT 均值，流式场景里**TTFT 才是体验的命门**——首字 3 秒用户觉得"在工作"，首字 30 秒用户觉得"死机了"。

我的指标清单分三块：**模型侧**——TTFT、token/s 吞吐、单请求总时延，都要记 P50/P95 分位数；**工具侧**——docling 解析耗时的独立测量（按文档大小分档），这个特别重要，因为**它和模型耗时是两类问题两个优化方向**，混在一起看总时延会误诊；**系统侧**——并发成功率、API 限流触发情况（429 错误率）、排队时延。旧题库 Q39 那套 LLM API 压测口径（梯度加压、限流边界探测）直接复用。

有两个平台特有的测试设计：**一，超时预算验证**——我的 sse_read_timeout=600 是一个显式的工程假设："解析 P95 耗时 < 600 秒"。性能测试要专门验证这个假设：拿最大预期文档压测，如果 P95 解析耗时逼近 600，说明预算设计有风险，会出现"客户端超时断开、但解析还在跑"的幽灵任务——**性能测试的一个职责就是验证参数不是拍脑袋**。**二，成本随并发的关系**——并发上去之后 token 消耗、缓存命中率的变化，这决定团队化部署的成本模型。

**追问预警**：
1. "TTFT 慢，优化手段有哪些？"——接法：模型侧换快档位/缩短首步工具链（先回一句话再解析）、缓存；工具侧解析预热、并行化——分层归因再动手。

### B39 · 你平台的 pytest 测试目前覆盖了什么？为什么先测这些而不是别的？

**推荐答案**：
现状：tests/ 里两组测试——**test_file_parser**（文件解析：合法/非法路径、格式处理）和 **test_pdf_parse_middleware**（PDF 解析中间件：解析结果的结构与关键字段断言）。conftest.py 统一 fixture。

为什么先测它们，我有一个明确的优先级公式：**优先级 = 确定性 × 变更频率 ÷ 断言成本**。拆开讲：**确定性**——文件解析和中间件没有 LLM 参与，输出确定，传统断言直接适用，测试写了就稳定绿，不会天天 flaky；**变更频率**——它们是依赖链的底座：依赖升级（docling/库版本）、格式边界变化都会动到这里，回归价值最高；**断言成本**——golden 比对和结构断言写起来便宜，一次投入长期复用。三者相乘，这就是 ROI 最高的起点。

反过来解释为什么不先测 LLM 层：LLM 生成质量用 pytest 断言既贵又不稳定（逐字断言必挂，性质断言要依托评测集基础设施），**在评测集建好之前写 LLM 层的自动化测试是伪覆盖**——测试挂了分不清是回归还是随机性，这种测试是负资产。所以我的顺序是：确定性组件 pytest 先行（已完成）→ 半确定组件 golden 比对（进行中）→ 概率组件评测集（规划中，B33-B34 详述）。

这个题我想传达的是**测试策略思维**：不是"测得越多越好"，而是"每一分测试投入买多少回归保护"——这是我从传统测试十几年带过来的、在 AI 时代更值钱的能力。

**追问预警**：
1. "你的 pytest 在 CI 里跑吗？"——接法：如实说当前本地跑 + 提交前手动跑，规划接 CI（uv 生态下配 GitHub Actions 很轻）——别吹已经有的。

### B40 · "AI 生成用例的可执行率"这个指标你会怎么定义和计算？分子分母各是什么？

**推荐答案**：
我的定义：**可执行率 = 无需人工修改即可直接执行的用例数 ÷ 生成的用例总数**。关键在分子里"可直接执行"的判定口径，我定得很死：**步骤可操作**（执行者不需要猜"如何操作"）、**预期可判定**（预期结果是明确的可观察行为，不是"界面正常"这种模糊描述）、**前置可满足**（前置条件描述的环境和数据是可构造的）。三条都满足才算分子，人工改了一个字都算分母里的"不可直接执行"。

这个口径的设计要点是**把"人的隐性补全"显性化**——人工执行用例时其实一直在做脑补（这个"操作购物车"是指点击加号还是输入数字？），AI 用例的问题就是需要补全的地方多。可执行率量的就是"距离免补全有多远"。

两个必须澄清的口径陷阱：**一，执行通过 ≠ 用例正确**——用例跑挂了可能是环境问题，也可能是真发现了 bug（这反而是好用例）；所以可执行率管的是"能不能照着跑"，不预判"跑的结果"。**二，统计必须抽检而不是全量**——按 P0/P1/P2 分层抽样执行，P0 全检、P2 抽检，统计成本可控。

公司项目里我们就是靠这个口径把用例准确率从 50-60% 做到 80%+ 的：先量化（每个版本抽检统计）、再归因（哪类缺陷占大头：步骤模糊？预期缺失？）、再定向优化 prompt 对应规则、再复测——**指标的意义不是汇报，是给优化指路**。个人平台我沿用了同一套口径。

**追问预警**：
1. "80% 之后为什么涨不动了？剩的 20% 是什么？"——接法：主要是强业务上下文依赖的用例（需要历史版本知识、线下约定），这类靠 prompt 解决不了，要么人写要么给模型喂更多上下文——承认边界反而加分。

### B41 · prompt 也是一种"代码"，你怎么做 prompt 的版本管理和回归？

**推荐答案**：
我的立场是**把 prompt 当有行为的代码资产管**，仓库里的实践是现成的：**czy_prompt/ 目录**专门存 prompt 及其演进版本，src/agents 下 test_case_agent_1.py 和 test_case_agent.py 两个文件就是新旧两版的对照——任何时刻都能 diff 出"这版改了什么、为什么改"。

具体管理制度四条：**一，prompt 进版本库**，和代码同 repo 同分支管理，改 prompt 走和改代码一样的提交规范——写清变更动机（修哪个 bad case、预期改善什么指标），杜绝"感觉改一下试试"。**二，版本与效果绑定**——每个 prompt 版本记录对应的评测结果（可执行率、臆造率等关键指标），形成"版本-效果"曲线，让 prompt 演进有据可查。**三，固定集回归**——B17 详述的双跑 diff + 分层性质断言：编号规则、三类场景、边界覆盖、格式完整性，旧版达标项新版必须达标，这是防劣化的门禁。**四，回滚能力**——因为版本都在库里，任何一个版本出问题可以精确回滚到上一个稳定版，而不是"改回来试试"。

一个我特别想强调的认知：**prompt 的行为是"概率性代码"**——同样的 prompt，模型升级、温度变化、上下文长度不同，行为都可能漂移。所以 prompt 的版本管理要比代码多管一层：**模型版本的绑定关系**——哪个 prompt 版本配哪个模型版本验证过的，要记录，模型一升级全量 prompt 回归就要跑一遍。这在公司项目里我们叫"prompt 回归门禁"，个人平台是轻量实现，机制是完整的。

**追问预警**：
1. "多人协作改 prompt 冲突怎么办？"——接法：prompt 单一 owner + 变更评审（bad case 证据先行），prompt 的"代码评审"评的是变更动机和回归证据。

### B42 · 算一笔账：AI 生成用例 vs 人工写用例，成本收益怎么算？什么场景 AI 划算、什么场景不划算？

**推荐答案**：
我的账本三栏：**AI 成本 = token 费 + 人工修正成本 + 平台维护摊销**；**人工成本 = 全人工写用例的工时 × 人力成本**；**隐性收益**（容易被漏算的部分）= 覆盖一致性（人不漏边界、不因疲劳漏场景）+ 知识沉淀（方法论固化在 prompt 里不随人员流动流失）。

拿公司的实际口径算：用例产出**从 1-2 天压缩到 2 小时**——这是"生成+人工修正"的总时长，其中人工修正是关键诚实项：AI 生成 20 分钟，测试同学花 1 个多小时校对修正（对照可执行率 80% 的口径，约两成用例需要人工干预），**但即便把修正算足，仍是数量级的提效**。个人平台的账我也能现场算：单文档 token 成本（B27 那笔账）+ 修正工时，对比人工半天到一天。

**场景适配**是这题的重头：AI 划算的场景——**文档结构清晰、字段约束明确**（接口文档、带表格的功能说明）、**CRUD 和表单类逻辑**（边界值规则能机械套用）、**回归性文档**（迭代文档改版后重生成快）；AI 不划算的场景——**探索期需求**（文档本身还在变，生成了也白生成）、**强业务历史依赖**（逻辑在人的脑子里和聊天记录里，文档没写——这正是那 20% 涨不动的部分）、**极小改动**（改个按钮文案重新走生成流程，不如手改两条用例）。

最后一句价值判断：**这笔账最大的战略收益不是省工时，是把测试同学从"写用例"解放到"想策略"**——测试设计的经验和判断花在风险最高的地方，这部分是 B47 的主题。

**追问预警**：
1. "你怎么说服团队里抗拒用 AI 的老测试？"——接法：不说服，先用边界值场景做出示范（AI 最强、人最容易漏的领域），让对比数据说话。

### B43 · AI 生成的测试用例有版权或合规问题吗？比如喂给模型的文档是公司的、生成的用例归谁？

**推荐答案**：
这个问题分**输入侧**和**输出侧**两本账，我在选型时都实际考虑过。

**输入侧是更紧迫的**：需求文档是公司核心资产，进模型前三个检查点：**一，训练用途**——所选 API 的条款是否承诺"用户数据不用于训练"（主流商用 API 都有此承诺，但免费/测试通道可能不同，要看清条款）；**二，数据出境与合规**——海外模型 API 意味着数据出境，这在很多公司是红线，**这是我选国产 DeepSeek 的重要理由之一**（呼应 B25 的选型逻辑，合规不是技术参数但是一票否决项）；**三，脱敏分级**——涉及真实用户数据的文档（比如我轨迹比对项目里的运单数据）进模型必须脱敏，这条在个人平台尤其要自觉：**个人项目绝不能拿公司真实文档做测试**，我用的是电商购物车这类自造/公开文档，这条纪律我守得很死。

**输出侧**：AI 生成内容的著作权在法律上仍有争议——多数法域认可"纯 AI 生成无人类创造性贡献"的内容难以获得完整著作权保护。但用例场景实际风险低：用例是公司**内部**测试资产，不作对外发表和商业授权，归属争议基本不触发；真正要注意的是**对外场景**——如果用例、测试报告要对外发布或开源，就需要审视内容来源。另外一层：生成用例里如果引用了真实用户数据（从缺陷单里带出来的），同样要脱敏，这是数据合规不是版权问题。

一句话收束：**测试工程师做 AI 工具的第一课是数据纪律**——什么能进模型、什么不能，这条线比任何技术选型都优先。

**追问预警**：
1. "公司要私有化部署你怎么建议？"——接法：数据敏感度分级——核心数据私有化（开源模型+自有 GPU），一般场景 API——顺势展现 B49 的成本视角。

### B44 · 你的评测集如果长期拿来跑回归，模型会不会"对着评测集过拟合"？怎么防评测集泄漏？

**推荐答案**：
会，而且这是所有评测体系的宿命问题——**你优化什么，什么就不再客观**。具体到我的场景两条泄漏路径：**一，prompt 迭代过拟合**——我看着评测集的 bad case 改 prompt，改着改着 prompt 变成了"针对这 50 份文档的专用答案"，评测分虚高，第 51 份新文档现原形；**二，评测集进训练**——如果未来做微调，评测样本混进训练集就是直接作弊，模型"背过考卷"。

我的防护体系五条：**一，holdout 保留集**——评测集切两块：80% 是"开发集"用于日常迭代，20% 的 holdout **只在大节点评估用**（版本发布、模型更换），平时迭代根本看不到它——这是防过拟合的核心机制。**二，持续换血**——新 bad case、新文档类型定期入库，老样本降权或轮出，评测集是活水池不是标本馆。**三，盲测纪律**——prompt 优化时不知道哪些 case 属于评测集（评测集样本打乱混入日常测试流），避免"对着答案改"。**四，权限隔离**——评测集与 prompt 开发在流程上隔离，微调场景下训练数据管道和评测集管道物理分开并做样本 hash 去重。**五，外部校准**——定期用"全新分布"的文档（换个业务域）做泛化抽查，如果开发集分数涨、泛化分数跌，就是过拟合的确诊信号。

这个话题我多说一句本质：**评测集和 prompt 的关系，就是考卷和刷题的关系**——教育界怎么防刷题（新题型、能力导向出题、综合素质评估），评测工程就怎么防过拟合。测试工程师做评测体系，手里最值钱的就是这种"对度量系统本身的怀疑精神"。

**追问预警**：
1. "你的 holdout 现在切了吗？"——接法：如实说评测集还在建设中，holdout 机制是设计里的既定项——诚实比装完整重要。

## 七、情景与开放（B45-B50）

### B45 · 假如入职后公司让你从 0 搭一个 AI 测试平台，你会怎么规划？前 3 个月做什么？

**推荐答案**：
我刚好有一份现成答卷——czy-ai-system 就是"一个人、从 0 到闭环"的实操记录，所以我的规划不是纸上谈兵，是踩过坑之后的修正版。三阶段：

**第一阶段（0-3 个月）：单点 MVP，建立信任**。只选一个 ROI 最高、边界最清楚的场景——我会选"文档到用例"（理由：输入是现成的需求文档、输出有明确质量标准、价值可量化）。技术上刻意做简：单 Agent + 现成工具（MCP 生态）+ 基础 Web UI，**但评测基线必须从第一天就有**——先固定 20 份文档、人工标注基线用例、跑出第一版可执行率和臆造率，哪怕数字很难看。没有基线，后面所有优化都是玄学。里程碑是"一份真实文档进去，80 分用例出来，测试同学愿意用"。

**第二阶段（3-6 个月）：质量闭环 + 回归门禁**。评测集扩到 50+、LLM-as-judge 抽检（B35 的校准流程）、prompt 版本管理和回归（B41）、确定性组件 pytest 全覆盖——让平台质量**可度量、可回归、可交接**。同时开始接入团队真实工作流（用例导出到管理系统）。

**第三阶段（6 个月+）：场景扩展与平台化**。从用例生成扩到相邻场景（接口测试生成、造数——我在公司有现成经验），多 Agent 拆分（评审 Agent、修正 Agent），权限和成本治理跟上，从"我的工具"变成"团队的平台"。

贯穿三阶段的铁律：**先窄后宽、评测先行、每周可演示**。要复用的公司经验：多 Agent 流水线的 Coordinator 编排、防幻觉三板斧、以及"1-2 天→2 小时"背后那套落地节奏——先跑通再优化，先可用再好用。

**追问预警**：
1. "第一版效果很差，业务方质疑怎么办？"——接法：提前管理预期——发布时就讲清这是基线版，给出一版到二版的提升计划和时间点，用迭代节奏换信任。

### B46 · 给你一个陌生的 Agent 系统，只有半天时间，你怎么快速摸底并给出测试方案？

**推荐答案**：
半天四小时，我的时间盒切五段，**每段都有明确产出物**：

**第一小时：跑通 happy path + 看 trace**。找 owner 要一个标准场景，完整跑一遍，重点看执行 trace：调了哪些工具、什么顺序、state 里流转了什么。目标产出：**系统的工具清单和数据流图**——这是后面所有测试的地图。顺手记录：哪些环节有日志、哪些是黑盒。

**第二小时：边界与异常**。测试工程师的肌肉记忆：空输入、超长输入、格式错误、非法参数直接打；然后是 Agent 特有的——**工具失败注入**（mock 工具返回错误/超时，看 Agent 是崩溃、死循环还是优雅降级）、多轮对话中的上下文越界。目标产出：**稳定性风险清单**（分级）。

**第三小时：安全摸底**。prompt 注入（用户消息里藏"忽略之前指令"）、工具滥用（诱导高频调用）、数据外泄路径（敏感信息是否会进工具调用参数）。目标产出：**安全风险清单**。这块我有公司"大模型能力边界"研究的积累（A45 有完整方法）。

**第四小时前半：质量与稳定性抽检**。同一输入多次采样看输出方差；构造两三个"有标准答案"的输入测准确性。目标产出：**质量基线初值**。

**最后半小时：汇总成摸底报告**——风险按"概率×影响"排级，给出测试优先级建议：哪些必须立即修（安全/稳定性 P0）、哪些进回归（边界集）、哪些需要建评测（质量类）。**明确说清半天的局限**：这是风险摸底不是完整测试，结论置信度对应样本量。

我的底气在于：这套流程的每个环节我在自己平台上都实操过（B18 的边界清单、B23 的安全用例、B37 的 E2E 分层），是从"被测方"视角反向打磨出来的"测人方"方法论。

**追问预警**：
1. "没有 trace/日志的黑盒系统怎么办？"——接法：降级为纯黑盒输入输出测试 + 用输出反推行为模式，同时在报告里把"可观测性缺失"本身列为 P0 风险。

### B47 · AI 都能写用例了，测试工程师的核心价值还剩什么？

**推荐答案**：
我的答案一句话：**AI 接管"执行"，人负责"判断"——而判断恰恰是更值钱的部分**。

拆开讲四个不可替代：**一，测试策略**——测什么、不测什么、资源投向哪里，这是风险决策，AI 没有责任主体，也没有业务上下文的价值排序能力。**二，质量标准的定义权**——什么叫"够了"、/release 的门槛建在哪，这是业务判断+风险偏好的综合，把这交给模型等于把方向盘交给没有利害关系的一方。**三，AI 输出的验收**——这一条最反直觉：**AI 用例生成能力越强，会验收它的人越稀缺**。我这套评测体系（评测集、judge 校准、可执行率口径）本身就是一个全新的专业能力栈——AI 时代测试工程师不是被替代，是被升级成"AI 质量的守门人"。**四，探索性与复杂场景**——AI 强在规则可枚举的领域（边界值、CRUD），弱在需要跨系统联想和历史经验的探索性测试，20% 涨不动的部分就是人的阵地。

一个类比：编译器取代了手写汇编，程序员的价值上升了不是消失了——因为**工具越强大，会用工具的定义问题的人越稀缺**。AI 之于测试同理。

我自己就是活证据：我这几年的轨迹就是从"执行测试"转向"定义怎么测 AI"——轨迹比对工具、多 Agent 流水线、这个用例平台，每一步都是把个人经验**产品化成系统**，让执行规模化，让自己往判断层走。所以别人问"AI 会不会取代测试工程师"，我的回答是：**会取代不会用 AI 的测试工程师，而这正是我的机会窗口**。

**追问预警**：

### B49 · 如果模型 API 明天涨价 10 倍，你的平台和业务怎么办？

**推荐答案**：
先给结论：**这不是危机是压力测试，我的架构里早就留了泄压阀**。分短期、中期、长期三层应对：

**短期（当天就能做）：换供应商**。我把模型封装在 src/core/llms.py 单点——ChatDeepSeek 一处定义全项目引用，换模型只改这一个文件。而且我不是"理论上可换"：智谱 GLM 我真实接过（zhipu_demo.py），切换是**验证过的路径**而不是纸面选项。要补的功课是换模型后全量 prompt 回归（B41 讲的版本绑定机制就是为这准备的——方法论 prompt 对模型的遵循能力敏感，换模型必须重跑评测）。

**中期：成本工程三板斧**。**缓存**——Agent 多轮调用中 system prompt 和已解析文档是不变前缀，吃 prompt caching 折扣（B27 讲过输入 token 被轮数放大，缓存收益被同样放大）；**结果缓存**——同一文档+同一 prompt 版本的生成结果直接命中，迭代场景重复生成很多；**上下文压缩**——需求点清单化（B14）天然降输入 token。这三板斧在涨价前就该做，涨 10 倍只是把优先级顶到眼前。

**长期：架构级选项**。**模型路由分层**——简单任务（格式校验、分类）走便宜的小模型，复杂生成才上旗舰，按任务价值分配模型预算；**自部署开源模型**——合规和数据敏感性高的场景本来就值得，成本从 API 计费变成 GPU 运维，量大了自部署反而便宜——但这个决策要做 TCO 测算，不能拍脑袋。

这题我真正想表达的认知是：**成本是架构设计出来的属性，不是运营时才补救的问题**。llms.py 那个单点封装，写它的时候就是为了今天这个假设——"模型选型是可逆决策"（B25 讲过）。涨价 10 倍淘汰的不是用 AI 的团队，是**把模型焊死在代码里**的团队。

**追问预警**：
1. "换模型后质量掉了怎么办？"——接法：评测集全量回归 + 分维度对比，质量掉在哪个维度（格式遵循？边界覆盖？）就定向补 prompt——这又回到评测先行。

### B50 · 你怎么看 AI 测试未来 3 年的趋势？测试工程师要提前储备什么？

**推荐答案**：
四个判断，每个都对应一个储备动作：

**判断一：Agent 评测会走向标准化**。今天"Agent 测试"没有业界统一语言——什么叫覆盖率、怎么评多步任务的成功率，各说各话。3 年内会出现类似传统测试的工具链和指标体系（Agent 界的"JUnit+SonarQuber"）。**储备**：现在就开始用评测集/可执行率这套自建体系的人，标准化来临那天就是最早的熟练工——我的平台就是干这个的。

**判断二："评测工程师"会成为一个真岗位**。AI 团队里会需要专门建评测、管数据、守质量门禁的角色——这个角色天然由测试工程师演化而来，因为它需要的标注方法论、抽样统计、质量审计全是测试的老手艺。**储备**：LLM-as-judge 校准、评测集防泄漏（B44）这些"评测的评测"能力，是这岗位的核心竞争力。

**判断三：AI 生成代码的责任边界会成为焦点**。AI 写的代码出了线上事故，责任在提示者、平台还是模型？3 年内行业会形成共识性流程——大概率是"AI 生成 + 人签收"，**签收标准就是测试**：AI 代码的测试覆盖、验收口径会成为流程刚需。**储备**：测 AI 生成的代码/用例的能力（验收 AI 输出）会从加分项变必选项。

**判断四：质量左移会移到 prompt 和数据层**。传统左移是需求评审、静态检查；AI 时代最上游的质量变量是 prompt 质量和数据质量——prompt review 会像代码 review 一样进流程，训练/评测数据的质量管控会成为新测试对象。**储备**：prompt 工程的规范感（B41 那套版本管理）+ 数据敏感度。

收个尾：这些趋势的共同点是——**不确定性本身成了被测对象**。传统测试对付的是确定逻辑里的缺陷，未来测试对付的是概率系统的质量。而我的整个职业轨迹——轨迹比对、多 Agent 流水线、用例平台——就是在给概率系统建质量体系。这不是我追风口，是风口长在我耕耘的地里。

**追问预警**：
1. "如果 3 年后趋势全错了呢？"——接法：核心能力是"给不确定系统建度量"这个元能力，趋势变了它不过时——展示的是底层逻辑不是预言。

# 增补部分 · AI 岗位共性题答案（B51-B68，2026-10-21）

> 增补来源：他人总结的 36 个 AI 岗位共性问题——18 个合并进既有条目（增补段见本章末尾），18 个全新作答如下。

### B51 · 为什么这个需求适合用 Agent，而不是普通业务代码？

**推荐答案**：
我的判断标准是三个条件同时满足才上 Agent：**输入非结构化、过程需要工具链、结果需要迭代推理**。用例生成恰好三条全中：需求文档是自然语言写的 PDF，表格、流程描述、隐含规则混杂——普通代码连"读懂"这步都写不出来，硬编码规则只能覆盖固定格式，换个客户的文档结构就崩；过程需要先解析文档（docling 工具）、再提取需求点、再逐点生成用例，是个多步工具链；而且生成过程中模型要根据解析结果动态决定下一步——需求点有 30 个就出 30 组用例，有 5 个就出 5 组，这个分支逻辑不可能穷举写死。反过来我也答得出**不适合 Agent 的场景**：输入输出都是确定性的（比如"给定运单号查轨迹"）、规则可枚举的（金额计算、格式校验）、毫秒级响应的（高频接口）——这些用普通代码更可控、更快、可测试。我的轨迹比对工具就是这么分层的：**字段比对用规则引擎（确定性），归因分析才用 LLM（长尾理解）**——Agent 化不是赶时髦，是按问题性质选工具。
**追问预警**：①"你的平台里哪部分其实不需要 Agent？"——答：文档解析（docling 是纯工具调用，单步确定性），只有"解析后到用例生成"这段才真正需要 ReAct 推理——能拆清边界更显功力。

### B52 · Agent 如何判断用户意图并选择不同处理流程？

**推荐答案**：
两个项目两种做法，正好说明意图路由按复杂度选型。**czy 平台是单 Agent 简单意图**：场景收敛（进来的都是要生成用例的），不需要复杂路由——模型读 system prompt 就知道先调 docling 解析再生成，意图判断退化成了"流程内步骤选择"，这叫**用场景收敛换掉路由复杂度**，是单 Agent 架构合理的核心论据。**公司多 Agent 流水线是显式意图路由**：入口有 triggers/anti_triggers 双向匹配——正向关键词（"接口测试""接口需求测试"）触发对应流水线，反向排除（疑问句、商量语气、功能/性能等不相关词）拦截误触发；命中后 Coordinator 按意图把任务派给对应 Skill 驱动的子 Agent。这里有个实战教训：早期纯靠正向关键词，同事聊天"要不要用流水线跑一遍"就把流水线触发了——后来加了**句式识别**（疑问/商量语气拦截）才把误触发清零。所以我的方法论是：**意图路由的成本要匹配误触发的代价**——单场景用收敛，多流程用关键词+句式+白名单三层，别在简单场景上过度设计路由。
**追问预警**：①"意图识别用模型分类不行吗？"——行但贵：轻量意图关键词够用就别上模型，"准确率和成本的平衡"是工程判断。

### B53 · 执行到一半中断，状态如何保存和恢复？

**推荐答案**：
LangGraph 对这个问题有原生答案，我分三层讲。**第一层：状态存在哪**——Agent 的全部运行状态就是 MessagesState 里的 messages 列表（系统指令、用户输入、模型思考、工具调用和返回都在里面），LangGraph 的 **checkpointer 机制**把每一步之后的 state 快照持久化，每条会话用 **thread_id 隔离**——一个 thread 就是一条可恢复的完整执行线。**第二层：怎么恢复**——进程重启或执行中断后，客户端带同一个 thread_id 重连，LangGraph 从 checkpoint 加载 state 继续，而不是从头跑；前端 web 会话正是靠这个机制支持多轮对话的——上一轮"解析了文档、出了部分用例"，下一轮"补一下异常场景"，模型记得之前发生的一切。**第三层：我主动设计的恢复边界**——真正不可恢复的是外部副作用：如果工具已经执行了写操作（比如用例入库）然后中断，重放就可能重复执行，所以我的设计原则是**把"可重试的读"和"不可重放的动作"分开**：文档解析可以随便重跑（幂等），对外的写动作要么设计成幂等（同输入同结果），要么在执行前落任务台账，恢复时先查台账再决定是否重放——这个思路和我在公司做 130 万运单比对工具的"修复流水表"是同一个幂等设计。
**追问预警**：①"checkpoint 用什么存储后端？"——开发模式内存/SQLite 即可，生产用 Postgres/Redis；能说出"checkpointer 可插拔"即可。②"messages 全量存会不会膨胀？"——接 B14 上下文压缩，"存档全量、运行时裁剪"分开讲。

### B54 · 如何避免 Agent 死循环或重复调用同一个工具？

**推荐答案**：
ReAct 架构的天然风险就是循环失控——模型反复调同一个工具、每次拿到一样结果还不死心。我设三道防线：**第一道：轮数硬顶**——LangGraph 的 recursion_limit（节点/步骤上限）是兜底保险，超限直接抛异常终止，保证最坏情况有界；这是"永远不能撤掉的一道闸"。**第二道：重复检测**——对话历史里 messages 本身就记录了每次工具调用的参数和返回，模型理论上"看得见"自己调过；但光靠模型自觉不够，工程上可以做调用监控：同一工具+同样参数连续调用 N 次（阈值 2-3）就注入提示或直接熔断——我平台的场景里 docling 解析同一文档调两次还没结果，说明解析服务出问题了，再试十次也一样，此时正确动作是报告用户而不是硬刚。**第三道：prompt 层的终止条件**——我的 system prompt 里写了明确的工作流程和终止逻辑：解析完成→梳理需求点→生成用例→输出，每步有"完成判定"（解析结果完整即可停止读取、需求点覆盖即可停止拆解），减少模型在步骤间来回震荡。另外 ReAct 有个天然终止机制可以利用：**模型不再发起工具调用、直接输出文本，循环即结束**——所以 prompt 里"完成后直接输出最终答案"这句不是废话，是给模型的明确退出信号。
**追问预警**：①"熔断后用户看到什么？"——错误信息+已完成的部分结果+建议（重新上传/稍后重试），"失败要体面"呼应我 A25 踩坑教训。

### B55 · MCP 中设计了哪些 tools？每个 tool 的粒度怎么确定？

**推荐答案**：
先说现状再说原则。**czy 平台**：当前只有一个 docling 解析工具——粒度是"一次调用完成一种文档类型的完整解析"，输入文档路径、输出结构化内容，单一职责。**公司流水线**：5 个 Skill 对应 5 个交付物（需求分析、测试点、用例生成、用例评审、报告生成），粒度是**"一个交付物一个工具"**。从这两个实践我沉淀出三条粒度原则：**① 单一职责**——一个 tool 只做一件事，做的事要能用一句话说清；docling 只管"解析"，不管"生成"——职责混了，模型调用时会犹豫，出错时也说不清哪步坏。**② 参数可校验**——参数少而明确（路径、格式），能在调用前做合法性检查；参数超过 5 个说明这个工具干的事太多，该拆。**③ 返回可结构化**——返回值是模型要读的 Observation，结构化返回（分段、带类型）让模型好消化，一团乱文本会放大下一轮的误判。反例我也踩过思考过：如果把"解析+生成用例"做成一个大工具，看似调用次数少，实际把 Agent 的推理空间压没了——模型失去了"看到解析结果后调整生成策略"的机会，ReAct 的价值就丢了。**粒度的本质是：把决策点留给模型，把执行单元做小**。
**追问预警**：①"后续平台会加什么工具？"——答：用例入库/模板管理类工具，但"先有真实需求再加工具，不为凑数扩工具箱"。

### B56 · 为什么使用 RAG，而不是全文检索或直接把文档放进上下文？

**推荐答案**：
三种方式对应三个不同问题，我按"为什么不用另外两种"讲。**为什么不用直接放上下文**：三个硬限制——token 窗口装不下（文档几十万字远超窗口）、成本不可持续（每轮对话都重传全量文档，token 成本随轮数线性涨）、相关性稀释（塞进去的内容越多，模型对每段的注意力越薄，答案质量反而降）。小规模场景直接放上下文确实可行（见 B57 的边界判断），但知识规模一上来这条路就死。**为什么不用全文检索（关键词/ES）**：关键词匹配解决不了**语义鸿沟**——用户问"包裹一直没更新怎么办"，正确答案是"轨迹停滞"相关的复盘文档，但两个表述没有一个关键词重合；线上问题应答工具的提问是业务人员随手打的，同义、口语、错别字是常态，关键词召回在这场景直接失效。**RAG 的核心增量**是 embedding 把问题变成语义向量做相似度检索，"意思接近"就能召回，这正是自然语言提问场景的刚需。所以选型逻辑一句话：**知识量小→上下文直塞；提问规范统一→关键词检索够用；自然语言任意提问+知识规模大→RAG**。我做线上问题应答工具选 RAG，就是因为提问方是业务和技术支持、表述五花八门，关键词方案我们评估过，召回率不达标才上的向量检索。
**追问预警**：①"RAG 和关键词检索结合吗？"——答：混合检索（向量+BM25 加权）是常见优化，长尾专有名词靠关键词、语义靠向量——知道这个说明真调研过。

### B57 · 文档数量不多时，还有必要使用 RAG 吗？

**推荐答案**：
这个问题我喜欢，因为答案是"**不一定，要看三个条件**"——敢说"不一定用"才是真懂。我的判断框架三条：**① 知识总量能不能装进上下文**——粗算 token：中文约 0.6-0.7 token/字，所有文档加起来在 3-5 万 token 以内、且单次对话只用得到其中一部分的，直接把相关文档塞 prompt 就够了，检索层纯属多余；**② 更新频率**——文档不常变的可以固化进 system prompt 或长上下文；频繁更新的才需要"外挂知识库+实时检索"的 RAG 架构；**③ 提问的多样性**——就那么十来个 FAQ、问法收敛，甚至一个"关键词→答案"映射表都能解决。拿线上问题应答工具复盘（⚠ 具体规模按真实情况核对）：如果当时缺陷复盘+答疑文档只有几十篇，先试过"全量塞上下文"，成本和效果可接受的话确实不必上 RAG——最后选了检索方案是因为文档在持续累积、提问方表述分散，两个条件都指向外挂检索。但架构上我留了余地：**入口层做成"先判断知识规模，小走上下文、大走 RAG"**的成本分层——RAG 不是技术信仰，是规模触发的基础设施。这个回答的潜台词面试官会喜欢：技术选型服务于问题，不服务于简历。
**追问预警**：①"你平台里用 RAG 了吗？"——答：目前没有——用例生成知识来自上传文档本身，文档内容直接进上下文，正是"不滥用 RAG"的自我实践。

### B58 · RAG 没有召回正确内容时，怎么定位和优化？

**推荐答案**：
我的定位方法论是**先分层，再四步**。**先分层**：让系统把"检索到了什么"单独吐出来（或查日志），直接肉眼判断——如果正确文档根本不在 top-k 里，是**检索层问题**；如果在 top-k 里但答案错了，是**生成层问题**（prompt 没用好检索内容）。很多人 RAG 出问题就调 prompt，其实八成是检索层根本没召回——分层避免在错的楼层修电梯。**检索层四步定位**：① **query 理解**——用户原话拿去检索效果差是常态（口语化、缺关键词），先看是否需要 query 改写（同义扩展、补主语）；② **切片边界**——最常见根因：答案在 A 片段、关键词在 B 片段，切片把语义单元切断了——调整切片大小/重叠，或按标题/段落结构切；③ **embedding 相似度**——换 embedding 模型（中文场景中文模型明显好于通用）、看相似度分数分布，如果正确文档的分数就在阈值边缘，调 top-k 和阈值；④ **硬规则兜底**——高频问题建关键词→文档的强制映射，检索之外开一条人工通道。**生成层优化**：检索内容在但答案错，一般是 prompt 没约束"只基于检索内容回答"——加忠实度约束、要求引用来源，错误答案宁可拒答。这套方法论我在 A47（RAG 三层评测）里有体系版，这里是排障实操版——**定位顺序永远是先确认"米"有没有，再评价"饭"做得好不好**。
**追问预警**：①"怎么建立'正确文档'的标注？"——用历史问答对+人工标注做评测集，跑命中率/MRR 量化检索质量——接 A47 指标。

### B59 · 会话记忆、执行状态、审计记录分别解决什么问题？

**推荐答案**：
三者经常被混为一谈，我按"**各自丢了会发生什么**"来辨析——最直观。**会话记忆丢了**：用户体验断裂——上句刚说过"生成登录模块的用例"，下句问"再把异常场景补上"，模型不记得"登录模块"指什么；记忆解决的是**连续对话的连贯性**，载体是 MessagesState 的 messages 列表，隔离靠 thread_id——它丢了对话还能继续，只是体验回到"每次都自我介绍"的状态。**执行状态丢了**：任务无法恢复——跑到第 3 步（文档解析完了、用例出了一半）进程崩了，重启后如果 state 没持久化，只能从头来；状态解决的是**断点恢复**，载体是 checkpoint 快照——它丢了系统还能跑，但长任务全部重来，token 成本翻倍、用户等待加倍。**审计记录丢了**：出问题无法追责和复盘——谁在什么时候给模型输入了什么、模型调了什么工具、返回了什么、花了多少 token，这些事后追溯的依据全没了；审计解决的是**可回溯与合规**，载体是外部日志链路——它丢了系统功能一切正常，但出了事故就是黑箱，"无法解释的 AI 系统"在生产环境是过不了安全审查的。一句话总结：**记忆管体验、状态管恢复、审计管追责**——三者是三个正交的需求，架构上就是三个独立的机制，别用一个 messages 列表顺手全干了（记忆够用、状态和审计要外挂）。
**追问预警**：①"你们的审计满足什么合规要求？"——按真实回答：内部质量追溯为主，若公司有等保/行业合规需求对齐条款。

### B60 · AI 应用如何做全链路可观测？一次请求经过哪些节点怎么追踪？失败从哪定位？

**推荐答案**：
可观测三支柱（logs、metrics、traces）在 AI 应用里的具体化：**Traces（链路追踪）——回答"一次请求经过了什么"**：LangGraph 生态的现成方案是 LangSmith——每条请求自动生成 trace 树：用户输入→模型第 N 次推理（含完整 prompt 和输出）→工具调用（docling 参数和返回）→最终输出，每一跳的耗时、token 都在；开发期 `langgraph dev` 控制台就能看 trace，生产接 LangSmith 或自建（把每次调用的 span 写 OpenTelemetry）。**Metrics（指标）——回答"系统健康度"**：我要盯四类：成功率（含按失败原因分类：超时/格式错误/内容拒答）、**TTFT**（首 token 时间，体验命脉）、token 消耗与成本（按用户/按场景分摊）、工具调用耗时分布（docling 的 P95——这是我设 sse_read_timeout=600 的依据，超时预算就该比 P95 大一个量级）。**Logs（结构化日志）——回答"事后查什么"**：每次请求记录请求 ID、thread_id、模型版本、prompt 版本——出问题时能按 ID 把三者对上。**失败定位顺序**：拿到 trace 先分层——工具层断没断（docling 超时/异常一眼可见）→模型层有没有正常输出（API 报错/内容截断/格式崩坏）→网络层（连接/限流 429）→prompt 层（指令冲突导致的怪行为，最隐性，靠 trace 里的完整 prompt 现场才能确诊）。**AI 应用比传统应用更依赖 trace**：因为中间多了"模型推理"这个黑盒步骤，没有 trace 就只能"重启试试"。
**追问预警**：①"采样还是全量记录 trace？"——答：开发全量、生产按比例采样+错误全采——成本意识。

### B61 · 审计追踪具体审计哪些信息？

**推荐答案**：
审计要素五件套，我按"出事后要能回答什么问题"倒推设计：**① Who & When**——谁（用户/会话 ID）、什么时间发起的请求：出事第一问永远是"谁干的、什么时候"。**② 输入摘要**——用户的原始输入要留档（含上传文档的指纹/存档，不只是路径——文档内容变了，路径审计就失效了）。**③ 输出摘要**——模型生成了什么，特别是工具调用的**参数和返回**：AI 系统的"动作"都藏在工具调用里，只记"调用了 docling"不记参数，等于没审。**④ 模型与 prompt 版本**——用的哪个模型、哪个版本的 system prompt：同输入不同版本输出不同，不记版本就没法解释"为什么当时是那个答案"。**⑤ 成本**——token 消耗和金额：既是财务审计也是滥用监控（某账号 token 突增 10 倍就是告警信号）。**留存设计**：审计日志与应用日志分离、追加写入不可篡改、保留期按合规要求（通常 6 个月-2 年）。我在公司流水线里的实践是**工具调用留痕**——anti_triggers 的每次拦截都记录（拦截原因+原文），既做误触发复盘也做审计——那套记录支撑了后来"误触发清零"的改进决策，审计的价值不只是合规，还是改进的数据源。
**追问预警**：①"输入含敏感信息怎么审计？"——接 B62：审计层存脱敏后的摘要，原文加密另存——审计与脱敏不矛盾。

### B62 · 敏感信息如何识别和脱敏？

**推荐答案**：
AI 场景的敏感信息处理我做三层：**输入层（识别+脱敏）**——进模型之前处理：规则识别（手机号/身份证/银行卡/邮箱的正则匹配，覆盖 90% 高频场景）+ NER 模型识别（人名、地址等非格式化敏感项）做兜底；识别后按类型掩码（手机号 138****5678）或替换占位符（保留数据形态、去掉数据实体）。**模型层（合规路径）**——选 DeepSeek/GLM 这类国产模型，数据不出境、符合国内合规要求，这是我模型选型里合规权重的实操体现（呼应 B25/B43）；真涉密场景就私有化部署，模型调用边界=数据边界。**留存层（日志脱敏）**——trace 和审计日志落库前再过一遍脱敏（呼应 B61："审计要留证据"和"日志不泄密"两个要求靠分层满足：摘要脱敏留审计、原文加密单独存）。我有现成的实战经验迁移：做压测时处理过线上数据脱敏（手机号/地址规则化替换、保留数据分布）——同一套方法论从测试数据迁移到 AI 输入，规则没变，变的只是应用位置。**一个 AI 特有的坑**：脱敏要在进 prompt 前做，而不是模型返回后再做——模型已经"看过"了，事后脱敏只保护了日志，没保护数据主体；这也是为什么脱敏层要放在输入管道里，做成中间件（和我的 pdf_parse_middleware 同一个架构位置）。
**追问预警**：①"掩码后的数据模型还能用吗？"——答：测试场景多数只需要"形态正确"不需要真实值（造数思维），关键场景用"可逆加密+处理完还原"保两全。

### B63 · 你平时如何使用 AI 完成一个完整需求？

**推荐答案**：
我有完整的工作流，而且 czy-ai-system 这个平台本身就是按这套流程开发的——全程拿它当案例。**第一步：规格先行**——动手前先写清楚"要做什么、技术约定、目录结构"，落成 CLAUDE.md（项目根目录那份就是）——AI 编程最大的坑不是代码错，是**你不知道自己要什么**，规格文档就是给 AI 的需求文档，这一步质量决定后面返工率。**第二步：骨架生成**——把规格喂给 Claude Code，生成项目骨架（目录、接口定义、配置），我先 review 骨架再放行——架构层的错误代价最大，必须人在最前面把关。**第三步：逐模块迭代**——一次让它做一个小模块（"先做 PDF 解析中间件"），小步快跑，每步我看得过来——**单元大了 review 不过来，AI 生成的代码就变成了我不理解的代码**。**第四步：测试验证**——关键行为写 pytest 固化（tests/ 里的解析中间件测试就是这么来的），AI 改坏了我能第一时间知道；这里我的测试工程师本行直接变成了 AI 编程的质量保障。**第五步：收尾 review**——整体过一遍命名、边界处理、和规格的偏差。这套流程的心得一句话：**AI 把"写代码"的时间压到接近零，把"定义清楚+验证对"的价值抬到最高**——恰好是我这种测试背景的人的主场，规格能力就是测试用例设计能力的迁移。
**追问预警**：①"哪些步骤你不用 AI？"——答：技术选型和架构决策——AI 给的选型建议平庸且可能过时，这些我查官方文档+自己 demo 验证（接 B66）。

### B64 · AI 编程和传统编程有什么区别？

**推荐答案**：
我从三个维度讲，最后一个维度是我的职业视角。**产物确定性**：传统编程，代码是你一行行写的，理论上可推理、可静态分析；AI 编程，代码是模型生成的——**大概率对，但你不能默认它对**，产物从"可推理的"变成"需要验证的"，所以质量保障手段从 code review 为主，升级为 review+自动化测试+静态扫描的组合拳。**技能重心**：传统编程拼语法熟练度和 API 记忆；AI 编程把这些下放给了模型，**人的价值上移到规格表达**——把"要什么"讲清楚的能力（需求描述、验收标准、边界定义）成了核心技能——说到底这就是测试分析和用例设计的能力，所以我认为**测试工程师转 AI 编程协作反而有天然优势：我们本来就是干"定义清楚什么是对的"这个活的**。**质量责任**：传统代码出 bug，锅是写的人的，定位链路清晰；AI 代码出 bug，可能是提示词、上下文、模型本身三层原因（接 B68），定位方法论变了——但**责任没变**：署名是你的，"AI 写的"不构成免责——这也是我做 AI 编码质量左移 4×N 矩阵的出发点：AI 参与编码后，质量检查必须跟着前移，不能让测试环节独自兜底。一句话：AI 编程不是"打字变快了"，是**软件工程的确定性边界整体上移了一层**——上游（规格）更重、下游（验证）更重，中间（打字）归零。
**追问预警**：①"那初级程序员怎么办？"——答：正态分布中间塌陷，两端更值钱——规格和验证能力要趁早练，别只练中间态。

### B65 · 如何保证 AI 生成代码的正确性和可维护性？

**推荐答案**：
我的体系四层，从轻到重：**第一层：静态扫描**——AI 代码照过 lint/类型检查/安全扫描（和测试左移体系里的编码环节检查同一套），这一层零成本，AI 代码的语法和规范问题基本在这层清掉。**第二层：单元测试**——关键行为用 pytest 固化：czy-ai-system 的解析中间件就是这么处理的——AI 帮我实现了 pdf 解析，我写的测试断言"给定样例 PDF，输出应包含这些关键结构"——**测试表达的是"我认为正确的行为"，AI 表达的是"它理解的正确"，两者对齐才算真正确**；以后无论 AI 怎么重构这段代码，行为跑偏了测试就红。**第三层：review 抽样**——按风险分级：核心链路全量 review，工具类/外围代码抽检——这是 4×N 矩阵"编码与评审"环节的日常应用：AI 生成即扫、评审环节人工复核，每个交叉点有明确质量动作。**第四层：可维护性专项**——AI 代码最大的可维护性风险是"**能跑但没人懂**"：我的对策是逼 AI 写注释和 docstring（规格里强制要求）、命名规范在 CLAUDE.md 里约定、复杂段落要求 AI 自己解释"为什么这么写"——**我 review 的不是代码怎么写的，是这个代码我接手后能不能改**。这套体系的底层认知：AI 生成把"写"的成本降到零，但"保证正确"的成本一点没降、反而因为量大了而上升——所以质量动作要自动化（扫描/测试）+ 风险分级（人只看核心），否则人成了 AI 的流水线瓶颈。
**追问预警**：①"AI 生成的测试代码可信吗？"——答：AI 写测试、我改断言——断言（什么是对的）必须人定义，AI 只负责表达。

### B66 · AI 生成了你不熟悉的技术方案，你会怎么验证？

**推荐答案**：
这个场景我刚好有完整实战——czy-ai-system 里的 LangGraph 和 MCP，在动手前都是我不熟的技术，我的验证路径四步：**第一步：官方文档对照**——AI 给的方案（比如"用 MultiServerMCPClient 连 docling"）我不直接信，先查 LangChain/LangGraph 官方文档确认这个 API 真实存在、参数含义与 AI 说的一致——**AI 最典型的幻觉是编造不存在的 API 或过时的用法**，官方文档是一票否决项。**第二步：最小可运行 demo**——langchain_demo 目录里那串 model_demo→tool_demo→agent_demo 就是我验证路径的化石：先用 30 行代码裸调模型（验证连通和基本行为）、再加一个工具（验证 Function Calling）、再跑通最小 Agent——**每个概念先用最小 demo 跑通，再往正式项目里用**；MCP 也是一样，mcp/ 目录里 stdio、HTTP、SSE 三个 demo 就是我对三种传输的逐一验证。**第三步：关键行为固化成测试**——demo 验证过的行为，写进 tests 固化（解析中间件的测试）——以后模型版本升级或 AI 重构时，这些"我验证过的事实"不会悄悄变质。**第四步：小流量先用**——不确定的部分先跑在非核心路径（study_agent 先试，确认没问题才进 test_case_agent 主链路）。这套方法论的内核就是我的老本行：**对不熟悉的系统，测试工程师的默认动作本来就是"最小复现+边界验证+断言固化"——AI 生成的陌生方案，在我这就是"一个待测系统"**。
**追问预警**：①"AI 给的方案比官方推荐还新怎么办？"——答：可能是真实的新实践，也可能是幻觉——以能跑通的 demo 为准，"跑通"是唯一仲裁。

### B67 · 你有没有沉淀自己的 rules、SPEC 或项目上下文？

**推荐答案**：
有，三件套，而且都有实物：**第一件：项目级 SPEC——CLAUDE.md**——czy-ai-system 根目录那份：项目定位、技术栈约定、常用命令、架构规则（"新增 Agent = 定义 create_agent + langgraph.json 注册一行"）——它解决"每次和 AI 对话都要重新解释项目"的问题，**上下文一次沉淀、终身复用**，AI 生成代码的架构一致性全靠它兜底。**第二件：工作流级 Skill——公司流水线的 5 个标准化 Skill**——需求分析、测试点、用例生成、评审、报告，每个 Skill 三段式结构（name/description/正文）+ 规则模块（禁止事项）+ **防踩坑模块**（缺陷复盘、业务规则、领域坑点回灌）——这是把"人和人协作的经验"变成"人和 AI 协作的资产"，而且是纳入团队 Prompt 体系的，不是我个人的小抄。**第三件：方法论级 rules——测试规范与 AI 编码质量左移**——全流程测试规范（需求到上线各环节的检查项）、4×N 矩阵（AI 生成代码的质量检查怎么分布到研发生命周期）——这些是"AI 时代怎么保证质量"的规则沉淀。三者的共性：**rules/SPEC 的本质是给 AI 的测试用例**——定义清楚"什么是对的"，AI 的输出才可验证；我一直说测试工程师做 AI 沉淀有天然优势，因为我们写用例的经验，直接迁移成写 SPEC 的能力。
**追问预警**：①"这些沉淀怎么维护更新？"——答：CLAUDE.md 随项目演进随手改；Skill 防踩坑模块随月度缺陷复盘迭代——沉沗物不更新就贬值，"活文档"。

### B68 · AI 生成代码发生错误时，你怎么定位是提示词、上下文还是代码问题？

**推荐答案**：
三源定位法，**顺序很讲究：先代码、再上下文、后提示词**。**第一步：先当普通 bug 查代码（约 50% 的问题在这层）**——AI 生成的代码也是代码：最小复现、看报错栈、单步调试——很多人 AI 代码一出错就怀疑"是不是 prompt 写得不好"，其实大部分就是普通的代码错误（空指针、边界、类型）——**别把 OOM 当玄学**。tests/ 里的单测在这一步就是最小复现的现成载体。**第二步：查上下文（信息够不够）**——如果代码逻辑本身没毛病但行为不对，查喂给 AI 的信息：相关文件给全了吗（它只看到一半改的）？上下文里有没有互相矛盾的旧代码？RAG/检索有没有把关键信息漏掉？——**AI 的错经常是"你给的信息的错"**；验证方法：把完整上下文重新喂一遍，看结论变不变。**第三步：查提示词（指令歧义）**——前两层都排除才到这：指令有没有歧义（"优化性能"没说什么指标）、多条指令有没有冲突（既要简洁又要详尽）、格式约束够不够明确——验证方法：**控制变量**——固定上下文和代码，只改 prompt 措辞跑对照，或换个模型跑同 prompt（区分"模型理解问题"和"表达歧义"）。这个顺序的设计逻辑：**按排查成本升序、按概率降序**——代码层排查最便宜、概率最高，prompt 层最隐性、成本最高，放最后。这也是我 debug 自己平台时真实走的路径——开发解析中间件时一个"偶发解析失败"，最后定位是上下文问题：文档超过一定长度时被截断，AI 没被告知有截断（真实的例子，说明第三层多隐蔽）。
**追问预警**：①"怎么预防而不是事后定位？"——答：spec 写清楚验收标准+边界行为（B63 第一步）、关键行为固化测试（B65）——预防的成本远低于三源排查。

## 既有条目增补（对应共性题清单的合并部分，2026-10-21）

> 以下 5 段是对现有条目的角度补充，背诵时与原答案合并使用。

**【B12 增补 · 输出格式错误怎么处理】**：输出格式错误单列一类：模型没按预期 schema 输出（Markdown 表格列错、JSON 带了注释）——处理三层：① 生成侧约束——prompt 里给明确格式模板（我的 system prompt 就有完整表格列定义），LangChain 生态可用结构化输出（structured output/with_structured_output）让格式在 API 层强制；② 校验侧拦截——输出先过格式校验（列齐全/编号连续），不合规直接打回重生成而不是流给用户；③ 重试侧兜底——格式错误重试 1-2 次，仍失败降级为"输出原始内容+提示格式异常"——**宁可用不完美的输出换确定性，不用崩溃换完美**。

**【B16 增补 · bad case 积累机制】**：bad case 我做成库而不是散落的聊天记录：每条记四要素——**输入（原文档/原问题）、输出（AI 实际产物）、问题分类（格式错/覆盖率缺/臆造/粒度不对）、修复动作（改 prompt 哪一段）**；按月复盘归类，高频根因驱动 prompt/规则迭代——这与我的缺陷复盘习惯是同一套动作，bad case 库就是"AI 系统的缺陷管理系统"。

**【B17 增补 · 知识库和模型变更的回归】**：B17 原答覆盖 prompt 回归，另外两类变更的回归策略：**知识库变更**（文档增删/切片调整/Embedding 模型升级）→ 先跑检索层指标回归（命中率/MRR，参照 A47），检索层没掉再看生成层——分层回归避免"整体感觉变差"说不清哪层的问题；**模型版本变更**→ 评测集全量回归+指标对比（通过率/臆造率/格式合规率），指标波动超阈值停下分析 bad case——模型升级"默认更好"是错觉，用例生成这种结构化任务上换模型必须重新评测。

**【B23 增补 · 用户权限、租户隔离与数据安全】**：B23 原答覆盖工具滥用与注入，权限/租户角度补充：**权限最小化**——Agent 只注册必需工具、敏感工具（写操作/外部发送）加二次确认；**租户隔离**——多租户场景每个租户独立的 MCP server 实例或按租户路由的鉴权层（工具调用带租户上下文，服务端校验资源归属），避免 A 租户的 Agent 读到 B 租户的文档；**数据不出域**——涉密租户走私有化部署，MCP 的进程隔离正好支持"解析服务部署在租户边界内"——这是 MCP 架构相对内嵌工具的天然安全红利。

**【B30 增补 · 答案可信度怎么判断】**：可信度判断三层实操：**① 可验证性优先**——要求输出带依据（用例要能追溯到文档需求点、归因要引用字段差异原文），无依据的判定存疑；**② 关键事实抽查**——输出里的数字、字段名、规则与源文档比对（我的规则校验层就是这个思想的代码化）；**③ 分歧检测**——同输入多次采样（温度>0），结果分歧大的条目降置信度转人工——共识即可信、分歧即存疑。判断为"不可信"的处理不是静默丢弃，是标注后进人工队列——信任机制要有出口，不能只有拦截。

### B69 · Prompt 和 Skill 有什么区别？（2026-10-23 增补，高频概念辨析题）

**推荐答案**：
一句话：**prompt 是对话，skill 是资产**。
四维区别：①**本质**——prompt 是一次交互的指令+上下文，解决"这一次怎么回答"；Skill 是把 prompt **工程化封装**后的可复用能力包，解决"这一类事怎么做"。②**生命周期**——prompt 会话内有效用完即弃，下次重贴；Skill 持久存在、跨会话复用、可版本管理。③**触发**——prompt 手动输入；Skill 自动触发（description/triggers 按意图路由）。④**结构**——prompt 自由文本；Skill 结构化模块：怎么干（正文 prompt）+什么时候干（触发）+别踩什么坑（规则/防踩坑模块）+按什么格式干（模板）。
**关键认知**：Skill 包含 Prompt 但不止 Prompt——多三样东西才成其为 Skill：①触发机制（场景到了自己出来，我的 triggers/anti_triggers）；②知识外挂（防踩坑、业务规则、缺陷复盘回灌——不占对话窗口按需加载）；③可演进（文件化、版本管理、团队共享——B41"prompt 当代码"）。
**我的实战锚定**：早期用裸 prompt 让 AI 生成用例——每次贴一大段要求，换个同事效果就不一样；后来沉淀成 5 个标准化 Skill（name/description/正文三段式+规则模块+防踩坑模块），纳入团队 Prompt 体系——**从 prompt 到 Skill 的演进，本质是把个人经验变成团队可复用资产**。czy-ai-system 的 system prompt 是嵌在 Agent 里的固定系统指令，Skill 是按需触发的能力包，两者在流水线里各司其职。
**追问预警**：①"system prompt 和 user prompt 呢？"——system 是角色与规则的固定层（Agent 人格和方法论），user 是每次的具体输入——分层不冲突。②"Skill 太多会互相误触发吧？"——正是我做 anti_triggers 的原因（B52 口径）。
