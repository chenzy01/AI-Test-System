# 需求类型分类与判断标准

需求清单中「需求类型」字段的取值，仅限以下 8 类。判定按「功能优先 → 按特征细分」的顺序，一条需求只归一类；跨类歧义登记疑点。

## 一、8 类定义与判断标准

| 类型 | 定义 | 判断标准（命中即归此类） | 典型示例 |
|------|------|------------------------|---------|
| 功能 | 描述「系统能做什么」的可操作能力 | 有明确触发入口（按钮/接口/事件）+ 处理逻辑 + 输出 | 用户提交订单、管理员导出报表 |
| 业务规则 | 约束行为/计算的规则，不独立成功能 | 描述「怎么算 / 怎么判 / 怎么流转」的规则 | 优惠上限 50%、订单 30 分钟未支付自动取消 |
| 数据 | 描述数据的字段、结构、取值范围 | 主语是数据字段 / 表结构 / 枚举 / 精度 | 手机号字段为 11 位数字、订单状态枚举 5 种 |
| 接口 | 描述系统间 / 模块间的接口契约 | 含请求方法、URL、入参、出参、错误码 | POST /api/order 入参 user_id，出参 order_id |
| 性能 | 描述系统的时间 / 容量 / 并发指标 | 含明确数值指标（响应时间 / TPS / 并发量） | 下单接口 P95 响应 ≤ 500ms |
| 兼容 | 描述在不同环境 / 终端 / 浏览器的适配要求 | 主语是运行环境矩阵 | 支持 iOS 13+ / Android 9+、Chrome 90+ |
| 安全 | 描述权限、鉴权、加密、审计等要求 | 涉及身份 / 权限 / 数据保护 / 审计 | 敏感字段脱敏、越权访问拦截 |
| 易用性 | 描述交互体验、提示、可访问性要求 | 主语是交互体验 / 文案 / 可访问性 | 表单校验错误提示定位到具体字段 |

## 二、判定顺序

1. 先看是否「有独立触发入口 + 处理逻辑 + 输出」→ 是则归「功能」。
2. 否则看是否「约束行为 / 计算的规则」→ 归「业务规则」。
3. 否则看主语是否「数据字段 / 结构」→ 归「数据」。
4. 否则看是否「接口契约」→ 归「接口」。
5. 否则看是否「含数值指标的性能要求」→ 归「性能」。
6. 否则看是否「环境适配」→ 归「兼容」。
7. 否则看是否「权限 / 安全 / 审计」→ 归「安全」。
8. 否则看是否「交互体验」→ 归「易用性」。
9. 仍无法归类 → 登记疑点（Q），标注「类型待确认」。

## 三、易混淆辨析

| 混淆对 | 辨析要点 |
|--------|---------|
| 功能 vs 业务规则 | 功能有独立入口；业务规则依附于某功能（如「下单」是功能，「优惠上限 50%」是下单这条功能上的规则） |
| 数据 vs 业务规则 | 数据的主语是「字段 / 结构 / 取值」；业务规则的主语是「计算 / 流转 / 判断」 |
| 性能 vs 功能 | 性能必须有明确数值指标；「支持 100 并发」是性能，「支持批量导出」是功能 |
| 安全 vs 功能 | 安全涉及身份 / 权限 / 数据保护；「管理员可导出」既是功能也是权限，按「功能」归类、权限约束记入「约束条件」 |
